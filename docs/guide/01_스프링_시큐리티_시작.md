# 가이드 01 · 스프링 시큐리티 시작

> **한 줄 요약**: API 3개(공지·내 정보·관리자 통계)를 가진 서버에 **스프링 시큐리티**를 붙이고, **보안 설정 클래스(`SecurityConfig`)**로 **공지는 누구나, 내 정보는 로그인한 사람만, 관리자 통계는 관리자만** 보이게 하는 기능 구현임

## 목표
- 보안이 없는 서버가 어떤 상태인지 먼저 봄 (관리자 통계까지 누구나 보임)
- 의존성 하나만 추가했을 때 스프링 시큐리티가 기본으로 무엇을 막는지 봄
- `SecurityConfig`를 직접 써서 필요한 만큼만 염
- **인증(누구인가)**과 **인가(무엇을 해도 되는가)**, **401**과 **403**의 차이를 화면에서 확인함
- 요청이 지나가는 보안 필터를 로그로 따라가 봄

## 완료 기준
- 화면(`http://localhost:3000`)에서 아래 표대로 나옴

| 아이디 | 공개 공지 | 내 정보 | 관리자 통계 |
|---|---|---|---|
| (비움) | 200 | 401 | 401 |
| user / 1234 | 200 | 200 | **403** |
| admin / 1234 | 200 | 200 | 200 |

- 서버 로그에서 `BasicAuthenticationFilter`, `ExceptionTranslationFilter`, `AuthorizationFilter`가 차례로 지나가는 것을 찾음

## 만들 API
| 요청 | 설명 | 누가 볼 수 있나 |
|---|---|---|
| `GET /api/public/notices` | 공지 목록 | 누구나 |
| `GET /api/me` | 로그인한 사용자 이름 | 로그인한 사람 |
| `GET /api/admin/stats` | 회원 수·오늘 매출 | 관리자(ADMIN) |

응답 예시:
```json
// GET /api/public/notices
[{"id": 1, "title": "11월 보안 교육 안내"}, {"id": 2, "title": "비밀번호 변경 주기 안내"}]
// GET /api/me
{"username": "user"}
// GET /api/admin/stats
{"members": 128, "todaySales": 3450000}
```

## 1. 개념 먼저

### 1-1. 보안이 하는 일 두 가지: 인증과 인가
건물 출입에 비유하면 이해가 쉬움.

| | 인증 (Authentication) | 인가 (Authorization) |
|---|---|---|
| 질문 | **너 누구야?** | **너 여기 들어가도 돼?** |
| 비유 | 출입구에서 사원증 확인 | 서버실 문은 관리자 사원증만 열림 |
| 실패하면 | **401** Unauthorized ("누군지 모르겠음") | **403** Forbidden ("누군지는 아는데 안 됨") |
| 오늘 코드 | 아이디·비밀번호 확인 | `hasRole("ADMIN")` |

- 이름은 401이 "Unauthorized(인가 안 됨)"인데 실제 뜻은 "인증 안 됨"임. 헷갈리기 쉬운 부분이라 **401 = 로그인 문제, 403 = 권한 문제**로 외워 둠
- 인증이 먼저, 인가가 나중임. 누군지 모르면 권한을 따질 수도 없음

### 1-2. 스프링 시큐리티는 "필터 묶음"임
```
브라우저 요청
  → [필터1] → [필터2] → ... → [필터16]   ← 스프링 시큐리티 (SecurityFilterChain)
  → 컨트롤러 (ApiController)
```
- **필터**: 요청이 컨트롤러에 닿기 전에 차례로 지나가는 검문소. 하나라도 막으면 컨트롤러까지 가지 못함
- **SecurityFilterChain**: 이 필터들을 줄 세운 것. 오늘 만드는 `SecurityConfig`가 "어떤 필터를 켜고, 어떤 주소에 어떤 규칙을 쓸지" 정함
- 오늘 로그에서 볼 주요 필터

| 필터 | 하는 일 |
|---|---|
| `CorsFilter` | 다른 주소(3000 → 8080)에서 온 요청을 허용할지 처리 |
| `BasicAuthenticationFilter` | `Authorization` 헤더의 아이디·비밀번호 확인 (인증) |
| `ExceptionTranslationFilter` | 뒤에서 난 보안 예외를 401/403 응답으로 바꿈 |
| `AuthorizationFilter` | 주소별 규칙(`permitAll`, `hasRole`…)으로 통과·거절 판정 (인가) |

### 1-3. 의존성만 넣어도 전부 잠김
- `spring-boot-starter-security`를 넣는 순간, 설정을 하나도 안 써도 **모든 주소가 로그인 필요**로 바뀜
- 로그인할 사용자가 없으면 안 되니까 스프링이 `user`라는 사용자와 **임시 비밀번호**를 만들어 서버 콘솔에 찍어 줌 (`Using generated security password: ...`)
- "기본은 다 막고, 필요한 곳만 연다"가 보안의 기본 원칙임. 오늘 실습 제목의 "막혀 보고, 필요한 만큼 열기"가 이 뜻임

### 1-4. 로그인 방식 두 가지: 폼 로그인과 HTTP Basic
| | 폼 로그인 (`formLogin`) | HTTP Basic (`httpBasic`) |
|---|---|---|
| 모양 | `/login` 화면에서 아이디·비밀번호 입력 | 요청마다 헤더에 `Authorization: Basic dXNlcjoxMjM0` |
| 로그인 기억 | 성공하면 쿠키(`JSESSIONID`)로 기억 | 기억 안 함. 요청마다 다시 보냄 |
| 오늘 쓰는 곳 | 브라우저 주소창으로 직접 열 때 | React 화면이 API를 부를 때 |

- `dXNlcjoxMjM0`은 `user:1234`를 Base64로 바꾼 것임. **암호화가 아니라 글자 바꾸기라 누구나 되돌릴 수 있음** → 실제 서비스에서는 반드시 HTTPS와 같이 씀
- 스프링 시큐리티는 요청 헤더를 보고 화면용인지 API용인지 구분함. 주소창 요청은 로그인 화면으로 보내고, React처럼 `X-Requested-With: XMLHttpRequest`를 붙인 요청에는 401만 돌려줌

### 1-5. CORS와 사전 요청(OPTIONS)
- **출처(Origin)**: `프로토콜 + 주소 + 포트`. `http://localhost:3000`과 `http://localhost:8080`은 포트가 달라서 **다른 출처**임
- **CORS**: 다른 출처로 요청할 때 "서버가 허락한 출처만 응답을 읽게" 하는 브라우저 규칙
- **사전 요청(Preflight)**: `Authorization` 같은 헤더를 붙여 다른 출처로 요청하기 전에, 브라우저가 먼저 `OPTIONS` 요청으로 "이 헤더 붙여서 보내도 되나요?"를 물음
  - 사전 요청에는 **로그인 정보가 없음**. 보안 필터가 이걸 먼저 보면 401로 막아 버림
  - 그래서 CORS 처리를 보안 검사보다 **앞에서** 해야 함 → `SecurityConfig`의 `.cors(...)` 한 줄이 이 일을 함
- CORS 자체는 4일차에 자세히 다룸. 오늘은 "왜 공개 API까지 실패했나"의 이유로만 봄

### 1-6. 오늘 쓰는 사용자: 메모리 사용자와 `{noop}`
- `InMemoryUserDetailsManager`: 사용자를 DB가 아니라 **서버 메모리**에 둠. 서버를 끄면 사라지지만 실습에는 충분함
- `UserDetailsService`: 스프링 시큐리티가 "이 아이디의 사용자 정보 줘"라고 부르는 창구. 오늘은 메모리 구현을, 2일차에는 DB 구현을 꽂음
- 비밀번호 앞의 `{noop}`: "암호화 안 함(no operation)"이라는 표시. 스프링 시큐리티는 비밀번호 앞의 `{...}`를 보고 비교 방식을 고름
  - 실습용임. 2일차에 `{bcrypt}`(해시)로 바꿈
- **역할(Role)**: `roles("ADMIN")`으로 넣으면 내부에는 `ROLE_ADMIN`으로 저장됨. `hasRole("ADMIN")`도 알아서 `ROLE_`을 붙여 비교함

### 1-7. 용어 정리
| 용어 | 쉬운 뜻 |
|---|---|
| 의존성 (dependency) | `build.gradle`에 적는 외부 라이브러리 |
| 빈 (Bean) | 스프링이 만들어서 들고 있다가 필요한 곳에 넣어 주는 객체. `@Bean` 메서드가 돌려준 값 |
| `@Configuration` | "이 클래스에는 설정용 `@Bean` 메서드가 있음" 표시 |
| Principal | 지금 로그인한 사람의 정보. 컨트롤러 파라미터로 받으면 스프링이 넣어 줌 |
| 세션 / `JSESSIONID` | 서버가 "이 브라우저는 로그인했음"을 기억하는 방법 / 그 열쇠가 담긴 쿠키 (5일차에 다시 봄) |
| Base64 | 글자를 다른 글자로 바꾸는 규칙. 암호화 아님 |

### 3-1. `SecurityDay1Application.java`
```java
package com.kyobo.lab;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

/**
 * 1일차 · 01 (스프링 시큐리티 시작)
 *
 * [역할] 서버 시작점. bootRun을 하면 이 클래스의 main()이 실행되어 스프링 서버(8080)가 뜸
 *
 * [알아야 할 것]
 * - @SpringBootApplication은 이 클래스가 있는 패키지(com.kyobo.lab)와 그 아래만 훑어서
 *   @RestController, @Configuration 같은 클래스를 찾아 등록함
 * - 그래서 ApiController, WebConfig, SecurityConfig도 반드시 같은 패키지(또는 하위)에 둬야 함
 * - 이 클래스에는 보안 코드를 넣지 않음. 보안 설정은 SecurityConfig가 따로 맡음
 */
@SpringBootApplication // 설정 읽기 + 같은 패키지의 빈 찾기 + 자동 설정을 한 번에 켬
public class SecurityDay1Application {

	public static void main(String[] args) {
		// 내장 톰캣을 띄우고, 찾아 둔 컨트롤러·설정 클래스를 모두 등록함
		SpringApplication.run(SecurityDay1Application.class, args);
	}
}
```
- `@SpringBootApplication`: 이 패키지(`com.kyobo.lab`)와 그 아래에 있는 `@RestController`, `@Configuration` 등을 찾아서 등록함. 그래서 다른 클래스들도 **같은 패키지 안에** 둬야 함

### 3-2. `ApiController.java`
```java
package com.kyobo.lab;

import java.security.Principal;
import java.util.List;
import java.util.Map;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

/**
 * 1일차 · 01 (스프링 시큐리티 시작)
 *
 * [역할] 오늘 지킬 대상인 API 3개. 보호 수준이 서로 다름
 *   - GET /api/public/notices : 누구나
 *   - GET /api/me             : 로그인한 사람
 *   - GET /api/admin/stats    : 관리자(ADMIN)
 *
 * [알아야 할 것]
 * - 이 클래스에는 보안 코드가 한 줄도 없음. 막고 여는 일은 컨트롤러 앞의 보안 필터(SecurityConfig)가 함
 * - 주소를 보호 수준별로 /public, /admin 처럼 나눠 둔 덕분에 SecurityConfig에서 주소 규칙 한 줄로 묶을 수 있음
 * - 데이터는 DB 없이 Map/List로 바로 만들어 돌려줌. 오늘은 "누가 볼 수 있나"만 봄
 */
@RestController         // 메서드가 돌려준 값을 JSON으로 바꿔 응답함 (화면 HTML이 아님)
@RequestMapping("/api") // 이 클래스의 모든 주소 앞에 /api가 붙음
public class ApiController {

	// 누구나 봐도 되는 정보 → SecurityConfig에서 permitAll()
	@GetMapping("/public/notices")
	public List<Map<String, Object>> notices() {
		return List.of(
				Map.of("id", 1, "title", "11월 보안 교육 안내"),
				Map.of("id", 2, "title", "비밀번호 변경 주기 안내"));
	}

	// 로그인한 사용자 본인 정보 → SecurityConfig에서 authenticated()
	@GetMapping("/me")
	public Map<String, String> me(Principal principal) { // 지금 로그인한 사람. 스프링이 넣어 줌
		// 보안이 없으면 로그인한 사람이 없어서 principal이 null임 (4-1에서 확인)
		return Map.of("username", principal == null ? "(로그인 정보 없음)" : principal.getName());
	}

	// 관리자만 봐야 하는 정보 → SecurityConfig에서 hasRole("ADMIN")
	@GetMapping("/admin/stats")
	public Map<String, Object> adminStats() {
		return Map.of("members", 128, "todaySales", 3_450_000); // 3_450_000 = 3450000 (_는 읽기용 구분자)
	}
}
```
- 주소를 `/api/public/**`, `/api/admin/**`처럼 **보호 수준별로 나눠 둔 것**이 핵심임. 그래야 3-5에서 주소 규칙 한 줄로 묶어서 막고 열 수 있음
- `Principal principal`: 스프링이 지금 로그인한 사람 정보를 넣어 줌. 보안이 없을 때는 `null`이라 `(로그인 정보 없음)`이 나옴
- **컨트롤러 안에는 보안 코드가 한 줄도 없음.** 막는 일은 컨트롤러 앞의 필터가 함 (1-2)
- `3_450_000`: 숫자 사이의 `_`는 읽기 좋게 쓰는 구분자임. 값은 `3450000`

### 3-3. `WebConfig.java`
```java
package com.kyobo.lab;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

/**
 * 1일차 · 01 (스프링 시큐리티 시작)
 *
 * [역할] CORS 규칙. React 화면(localhost:3000)이 이 서버(localhost:8080)의 API를 부를 수 있게 허락함
 *
 * [알아야 할 것]
 * - 포트가 다르면 다른 출처(Origin)라서, 서버가 허락하지 않으면 브라우저가 응답을 막음 (가이드 1-5)
 * - 이 설정은 스프링 MVC(컨트롤러 쪽) 설정이라 보안 필터보다 "뒤"에서 동작함
 *   → 시큐리티를 켜면 사전 요청(OPTIONS)이 여기까지 오기 전에 401로 막힘 (4-2)
 *   → SecurityConfig의 .cors(...)가 이 규칙을 보안 필터 앞쪽으로 끌어와서 해결함 (3-5)
 * - CORS는 4일차에 자세히 다룸
 */
@Configuration // 스프링 설정 클래스라는 표시. 서버가 뜰 때 읽어 감
public class WebConfig implements WebMvcConfigurer { // 스프링 MVC 설정을 바꾸는 창구

	@Override
	public void addCorsMappings(CorsRegistry registry) {
		registry.addMapping("/api/**")                            // /api로 시작하는 모든 주소에
				.allowedOrigins("http://localhost:3000")          // 이 출처에서 온 요청만 허락함
				.allowedMethods("GET", "POST", "PUT", "DELETE")   // 허락할 요청 방식
				.allowedHeaders("*");                             // Authorization 등 모든 헤더 허락
	}
}
```
- "`/api/**` 주소는 `localhost:3000`에서 온 요청을 허용함"이라는 CORS 규칙임
- 이 설정은 **스프링 MVC(컨트롤러 쪽)** 설정이라, 보안 필터보다 뒤에 있음. 3-4에서 이 때문에 문제가 생기고 3-5에서 해결함

→ 여기까지 쓰고 **4-1 확인**

### 3-5. `SecurityConfig.java`
```java
package com.kyobo.lab;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;
import org.springframework.security.web.SecurityFilterChain;

/**
 * 1일차 · 01 (스프링 시큐리티 시작)
 *
 * [역할] 오늘의 핵심 클래스. 스프링 시큐리티에게 세 가지를 알려 줌
 *   1. 주소별 규칙 (누가 어디에 들어갈 수 있나) → filterChain()
 *   2. 로그인 방식 (HTTP Basic, 폼 로그인)      → filterChain()
 *   3. 로그인할 수 있는 사용자 목록             → userDetailsService()
 *
 * [알아야 할 것]
 * - @Bean 메서드가 돌려준 객체를 스프링이 들고 있다가 보안 필터 체인에 씀. 직접 호출하는 곳은 없음
 * - 이 클래스가 없으면 "전부 로그인 필요 + 임시 비밀번호" 기본 설정으로 동작함 (4-2)
 * - 규칙은 위에서부터 차례로 보고 처음 맞는 하나만 씀. anyRequest()는 항상 맨 마지막
 * - 스프링 시큐리티 6 문법임. 블로그의 WebSecurityConfigurerAdapter, antMatchers, .and()는 옛날 문법
 */
@Configuration // 서버가 뜰 때 이 클래스의 @Bean 메서드들을 실행해서 결과를 등록함
public class SecurityConfig {

	// 보안 필터 묶음(SecurityFilterChain)을 만들어 등록함. 모든 요청이 컨트롤러 전에 이 필터들을 지남
	@Bean
	public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
		http
				// WebConfig의 CORS 설정을 보안 검사보다 먼저 적용함. 사전 요청(OPTIONS)이 401로 막히지 않게
				.cors(Customizer.withDefaults())
				// 주소별 인가 규칙. 위에서부터 차례로 보고 처음 맞는 규칙 하나만 씀
				.authorizeHttpRequests(auth -> auth
						.requestMatchers("/api/public/**").permitAll() // 공지는 로그인 없이 통과
						.anyRequest().authenticated())                 // 나머지는 로그인만 하면 누구든 통과 (항상 맨 마지막)
				.httpBasic(Customizer.withDefaults())  // Authorization: Basic 헤더로 로그인 (React 화면용)
				.formLogin(Customizer.withDefaults()); // /login 화면으로 로그인 (주소창용)
		return http.build(); // 위 설정대로 필터 묶음을 완성함
	}

	// 로그인할 수 있는 사용자 목록. 로그인할 때 스프링 시큐리티가 여기서 아이디로 사용자를 찾음
	// 1일차는 메모리 사용자 2명. 2일차에 DB 사용자와 BCrypt로 바꿈
	@Bean
	public UserDetailsService userDetailsService() {
		return new InMemoryUserDetailsManager( // 서버 메모리에 저장. 서버를 끄면 사라짐
				// {noop} = 암호화 안 함 표시. 빠지면 "PasswordEncoder mapped for the id null" 오류
				// roles("USER") → 내부에는 ROLE_USER로 저장됨
				User.withUsername("user").password("{noop}1234").roles("USER").build(),
				User.withUsername("admin").password("{noop}1234").roles("ADMIN").build());
	}
}
```

**`filterChain` 줄별 의미**

| 코드 | 의미 |
|---|---|
| `.cors(Customizer.withDefaults())` | CORS 필터를 보안 필터 묶음 앞쪽에 켬. 설정 값은 `WebConfig`의 것을 그대로 씀 |
| `.authorizeHttpRequests(auth -> ...)` | 주소별 인가 규칙 시작 |
| `.requestMatchers("/api/public/**").permitAll()` | 공지 주소는 로그인 없이 통과 |
| `.anyRequest().authenticated()` | 나머지는 로그인만 했으면 통과 (**누구든**) |
| `.httpBasic(...)` | `Authorization: Basic ...` 헤더로 로그인 허용 (React 화면용) |
| `.formLogin(...)` | `/login` 화면으로 로그인 허용 (주소창용) |
| `return http.build();` | 위 설정으로 필터 묶음을 만들어 빈으로 등록 |

- `Customizer.withDefaults()`: "따로 바꿀 것 없이 기본값으로 켜 줘"라는 뜻
- `auth -> auth....`: 람다식. `auth`라는 규칙 작성 도구를 받아서 규칙을 이어 붙임
- `@Bean`으로 `UserDetailsService`를 직접 등록했기 때문에, 3-4에서 콘솔에 찍히던 임시 비밀번호가 **더 이상 안 나옴**
- `throws Exception`: `http.build()`가 예외를 던질 수 있다고 선언되어 있어서 붙임

**블로그 코드와 다를 때**
- `extends WebSecurityConfigurerAdapter`, `antMatchers(...)`, `.and()` → 스프링 시큐리티 5 이전 문법임. 지금(6)은 위처럼 `SecurityFilterChain` 빈 + 람다로 씀

→ 서버를 다시 시작하고 **4-4, 4-5 확인**

### 3-6. `SecurityConfig.java`에 관리자 규칙 추가
`permitAll()` 줄 바로 아래에 한 줄을 추가함.
```java
				.authorizeHttpRequests(auth -> auth
						.requestMatchers("/api/public/**").permitAll() // 공지는 로그인 없이 통과
						// 로그인한 사람 중에서도 ADMIN만 허용. 좁은 규칙이라 anyRequest()보다 위에 둠
						// hasRole("ADMIN") → 내부의 ROLE_ADMIN과 비교함 (ROLE_은 자동으로 붙음)
						.requestMatchers("/api/admin/**").hasRole("ADMIN")
						.anyRequest().authenticated())                 // 나머지는 로그인만 하면 통과 (항상 맨 마지막)
```
- 규칙은 **위에서부터 차례로 보고, 처음 맞는 규칙 하나만** 씀
  - 그래서 좁은 규칙(`/api/admin/**`)을 위에, 넓은 규칙(`anyRequest()`)을 항상 맨 아래에 둠
  - `anyRequest()` 아래에 규칙을 더 쓰면 서버가 뜨지 않음 (4장 "막히면" 참고)
- `hasRole("ADMIN")`: 내부의 `ROLE_ADMIN`과 비교함 (1-6). `hasRole("ROLE_ADMIN")`이라고 쓰면 오류가 남

→ 서버를 다시 시작하고 **4-6 확인**

| 임시 비밀번호 줄이 안 보임 | 콘솔을 위로 올려 `generated`로 검색 |
| `There is no PasswordEncoder mapped for the id "null"` | 비밀번호 앞의 `{noop}`이 빠짐 |
| 공개 공지는 200인데 내 정보가 401이 아니라 `요청 실패` | `.cors(Customizer.withDefaults())` 줄이 빠짐 |
| `Can't configure mvcMatchers after anyRequest` (코드는 `requestMatchers`인데 메시지는 이렇게 나옴) | 추가한 줄이 `anyRequest()` 아래에 있음. `anyRequest()`는 항상 마지막 |
| `ROLE_ADMIN should not start with ROLE_` | `hasRole("ADMIN")`으로 씀 (`ROLE_`은 자동으로 붙음) |
| 4-3을 다시 하려는데 로그인 화면이 안 나옴 | 이미 `JSESSIONID`로 로그인된 상태. `http://localhost:8080/logout`에서 로그아웃 |
| import가 빨갛게 보임 (IntelliJ) | `build.gradle`을 고친 뒤 코끼리 아이콘(Load Gradle Changes)을 누름 |

## 5. 알려진 한계 (면접에서 물어볼 만한 부분)
1. **비밀번호를 평문(`{noop}`)으로 저장함**
   - 저장소나 메모리가 털리면 비밀번호가 그대로 보임 → 2일차에 BCrypt 해시로 바꿈
2. **사용자가 코드 안(메모리)에 있음**
   - 회원가입이 불가능하고 서버를 끄면 사라짐 → 2일차에 DB 사용자로 바꿈
3. **HTTP Basic은 요청마다 비밀번호를 보냄**
   - Base64는 암호화가 아니라서 HTTPS가 없으면 그대로 노출됨. 요청이 많을수록 노출 기회도 늘어남 → 2일차에 세션 로그인, 5일차에 다른 방식과 비교함
4. **권한 규칙이 주소 단위뿐임**
   - "내가 쓴 글만 수정 가능" 같은 규칙은 주소만으로는 못 정함 → 3일차에 다룸
5. **CORS 설정이 `WebConfig`와 `SecurityConfig` 두 곳에 걸쳐 있음**
   - 지금은 `.cors()`가 `WebConfig` 값을 가져다 씀. 출처를 늘릴 때 어디를 고쳐야 하는지 헷갈릴 수 있음 → 4일차에 CORS를 보안 설정 쪽으로 모으는 방법을 봄
6. **CSRF 보호가 켜져 있지만 아직 확인하지 않음**
   - 오늘 API는 GET뿐이라 영향이 없었음. POST를 만들면 바로 403이 날 수 있음 → 4일차에 다룸

## 스스로 답해볼 질문
1. 인증과 인가는 각각 무엇이고, 실패하면 각각 몇 번 상태 코드가 나오는가 (면접 질문)

3. `authorizeHttpRequests` 안에서 규칙 순서가 왜 중요한가. `anyRequest()`를 맨 위에 두면 어떻게 되는가
4. `{noop}`은 무슨 뜻이고, 실제 서비스에서 쓰면 안 되는 이유는 무엇인가
5. HTTP Basic의 `Authorization` 헤더 값은 암호화된 것인가. 그렇다면/아니라면 무엇을 같이 써야 하는가
