# 가이드 03 · 인가: 누가 무엇을 할 수 있나

> **한 줄 요약**: 2일차 서버에 **게시판 API**를 붙이고, **URL 규칙(HTTP 메서드별) + 역할 계층 + 메서드 보안(`@PreAuthorize`) + 소유자 검사(`PostGuard`)**로 **글 목록은 누구나, 글쓰기는 회원만, 수정·삭제는 작성자 본인 또는 관리자만, 전체 삭제는 관리자만** 되게 하는 기능 구현임

## 목표
- "로그인했나?"(인증)만 보는 서버가 얼마나 위험한지 먼저 봄 (남의 글이 지워짐)
- 같은 주소라도 **GET · POST 별로 다른 규칙**을 줌
- **역할 계층**(`ADMIN > USER`)으로 "관리자는 회원이 하는 일도 다 함"을 만듦
- URL 규칙이 놓친 곳을 **메서드 보안**으로 막고, 어노테이션만 붙이면 **아무 일도 안 일어나는** 함정을 직접 봄
- URL로는 절대 못 정하는 **"내 글인가?"(소유자 검사)**를 만듦
- 401 · 403 응답을 **JSON 한 모양**으로 맞춤

## 완료 기준
화면(`http://localhost:3000`)에서 아래대로 나옴. 수정·삭제는 **로그인한 사람을 바꿀 때마다 서버를 재시작**하고 확인함 (4-6)

| 로그인 | 글 목록 | 글쓰기 | 1번 글(user 작성) 수정 | 2번 글(kim 작성) 수정 | 1번 글 삭제 | 전체 삭제 |
|---|---|---|---|---|---|---|
| (안 함) | 200 | 401 | 401 | 401 | 401 | 401 |
| user | 200 | 201 | 200 | **403** | 200 | **403** |
| kim | 200 | 201 | **403** | 200 | **403** | **403** |
| admin | 200 | 201 | 200 | 200 | 200 | 200 |

- [ ] 401 → `{"error":"로그인이 필요합니다"}`, 403 → `{"error":"권한이 없습니다"}`
- [ ] 서버 로그에서 "필터(URL 규칙)에서 거절"과 "메서드(`@PreAuthorize`)에서 거절"을 구분함

## 만들 API
| 요청 | 설명 | 누가 쓸 수 있나 |
|---|---|---|
| `GET /api/posts` | 글 목록 | 누구나 |
| `POST /api/posts` | 글쓰기 (본문 `{"title":"..."}`). 작성자는 로그인한 사람 | 회원 (USER, ADMIN) |
| `PUT /api/posts/{id}` | 제목 수정 | 작성자 본인 또는 ADMIN |
| `DELETE /api/posts/{id}` | 글 하나 삭제 | 작성자 본인 또는 ADMIN |
| `DELETE /api/posts` | 전체 삭제 | ADMIN |
| 2일차 API | 공지 · 내 정보 · 관리자 통계 · 회원가입 · 회원 목록 · 로그인 · 로그아웃 | 2일차와 같음 |

응답 예시:
```json
// GET /api/posts
[{"id": 1, "title": "user의 첫 글", "author": "user"}, {"id": 2, "title": "kim의 첫 글", "author": "kim"}]
// POST /api/posts  {"title":"새 글"}   (kim으로 로그인)
{"id": 3, "title": "새 글", "author": "kim"}          // 201
// DELETE /api/posts/1
{"deleted": 1}
// DELETE /api/posts
{"deleted": "all"}
// 거절될 때 (4-7 이후)
{"error": "로그인이 필요합니다"}                          // 401
{"error": "권한이 없습니다"}                              // 403
```
- 계정: `user` · `kim`(USER), `admin`(ADMIN). 비밀번호는 모두 `1234`. 서버가 뜰 때 글 2개(1번 user의 글, 2번 kim의 글)가 들어감

## 1. 개념 먼저

### 1-1. 인가는 세 겹으로 함
1일차의 인가는 "주소만 보고" 판단했음. 오늘은 더 안쪽까지 들어감.

| 겹 | 비유 | 판단 재료 | 오늘 코드 |
|---|---|---|---|
| ① URL 규칙 | 건물 출입문 | 주소 + HTTP 메서드 + 역할 | `requestMatchers(HttpMethod.POST, "/api/posts").hasRole("USER")` |
| ② 메서드 보안 | 방문 앞 | 실행하려는 메서드 + 역할 | `@PreAuthorize("hasRole('ADMIN')")` |
| ③ 데이터(소유자) 검사 | 서랍 자물쇠 | **DB의 실제 데이터** (이 글의 작성자) | `@postGuard.isAuthor(#id, authentication.name)` |

- ①은 필터(`AuthorizationFilter`)가 컨트롤러 **전에**, ②③은 서비스 메서드가 실행되기 **직전에** 검사함
- **③은 URL만 봐서는 절대 못 함.** `PUT /api/posts/1`이라는 주소에는 "누구의 글인지"가 없음. DB에서 1번 글을 꺼내 작성자와 비교해야 함
- 한 겹이 놓쳐도 다음 겹이 막도록 **겹쳐서** 지킴 (4-5에서 직접 봄)

### 1-2. 같은 주소, 다른 규칙: HTTP 메서드별 URL 규칙
```java
.requestMatchers(HttpMethod.GET, "/api/posts/**").permitAll()    // 읽기는 누구나
.requestMatchers(HttpMethod.POST, "/api/posts").hasRole("USER")  // 쓰기는 회원만
```
- `/api/posts`라는 같은 주소라도 **GET(읽기)과 POST(쓰기)는 위험도가 다름**
- `HttpMethod`를 안 쓰면 모든 메서드에 같은 규칙이 걸림
- `/api/posts/**`: `/api/posts`와 그 아래 전부 (`/api/posts/1` 등)

### 1-3. 역할 사이에는 자동으로 위아래가 없음 → 역할 계층
- `hasRole("USER")`는 "`ROLE_USER`를 **가진** 사람"이라는 뜻임. admin은 `ROLE_ADMIN`만 있어서 **거절됨** (4-2에서 직접 봄)
- 사람은 "관리자니까 당연히 되겠지"라고 생각하지만, 스프링 시큐리티는 문자열을 비교할 뿐임
- **역할 계층(`RoleHierarchy`)**: `"ROLE_ADMIN > ROLE_USER"`라고 알려 주면 "ADMIN은 USER 권한도 가진 것으로 침"
  - URL 규칙과 메서드 보안 **둘 다** 이 계층을 씀

### 1-4. 메서드 보안: 어노테이션은 "스위치"가 켜져야 동작함
```
컨트롤러 → [보안 대리인(프록시)] → PostService.deleteAll()
               └ @PreAuthorize("hasRole('ADMIN')") 검사. 통과해야 진짜 메서드를 부름
```
- `@PreAuthorize("...")`: "이 메서드를 **실행하기 전에** 조건을 검사하라"는 표시
- 그런데 어노테이션은 **그냥 메모(표시)**일 뿐임. 읽고 검사해 줄 장치가 있어야 함
- **`@EnableMethodSecurity`**: 그 장치를 켜는 스위치. 켜면 스프링이 `@PreAuthorize`가 붙은 빈을 **대리인(프록시)**으로 감싸서, 메서드 호출을 가로채 검사함
  - 스위치 없이 어노테이션만 붙이면 **에러도 경고도 없이 그냥 통과**함 → 가장 위험한 실수 (4-4에서 직접 봄)
- 프록시 방식이라 **바깥(다른 빈)에서 부를 때만** 검사함. 같은 클래스 안에서 `this.deleteAll()`로 부르면 대리인을 안 거쳐서 검사가 빠짐 (6장 한계)

### 1-5. `@PreAuthorize` 안의 식 읽는 법 (SpEL)
```java
@PreAuthorize("@postGuard.isAuthor(#id, authentication.name) or hasRole('ADMIN')")
public Post update(Long id, String title) { ... }
```
| 조각 | 뜻 |
|---|---|
| `@postGuard` | 이름이 `postGuard`인 **빈** (`@Component("postGuard")`) |
| `.isAuthor(...)` | 그 빈의 메서드를 부름 → `true`/`false` |
| `#id` | 이 메서드의 **파라미터** `id` 값 (`update(Long id, ...)`의 `id`) |
| `authentication.name` | 지금 로그인한 사람의 아이디 (`Principal.getName()`과 같음) |
| `hasRole('ADMIN')` | ROLE_ADMIN을 가졌나 (역할 계층 포함) |
| `or` | 둘 중 하나만 참이면 통과 |
- 식 안의 문자열은 작은따옴표(`'ADMIN'`)로 씀. 바깥이 이미 큰따옴표라서
- 철자가 틀려도 **컴파일 에러가 안 남.** 실행할 때 500으로 터짐 (5장 "막히면")

### 1-6. 소유자 검사와 "작성자는 어디서 정하나"
- **IDOR(안전하지 않은 직접 객체 참조)**: 주소의 번호만 바꿔서(`/api/posts/1` → `/2`) 남의 데이터에 손대는 공격. 4-1에서 kim이 user의 글을 지운 것이 이것임
  - **화면에서 삭제 버튼을 숨겨도 소용없음.** 1일차에 본 것처럼 API는 `curl`로 직접 부를 수 있음. 막는 건 반드시 서버가 함
- 글을 쓸 때 **작성자는 요청 본문이 아니라 로그인 정보(`Principal`)에서 정함**
  - 본문에서 `{"title":"...", "author":"admin"}`처럼 받으면 남의 이름으로 글을 쓸 수 있음
  - 그래서 `PostRequest`에는 `title`만 있음
- 소유자 검사 로직은 `PostGuard`라는 **작은 빈**으로 따로 뺌. `@PreAuthorize` 식이 짧아지고, 다른 곳에서도 재사용 가능

### 1-7. 401 · 403 응답은 누가 만드나
```
어디선가 거절 (AuthorizationFilter의 URL 규칙 또는 @PreAuthorize)
  → ExceptionTranslationFilter (1일차 15번 필터)가 잡음
       ├ 로그인 안 한 사람 → AuthenticationEntryPoint → 401
       └ 로그인한 사람     → AccessDeniedHandler     → 403
```
- 기본 응답은 401은 **본문이 비어 있고**, 403은 스프링 부트 기본 에러 JSON(`{"timestamp":...,"status":403,...}`)임. 모양이 제각각이라 화면에서 다루기 불편함
- 이 두 처리기를 직접 바꾸면 **어디서 거절됐든 같은 모양**으로 돌려줄 수 있음 (4-7)

### 1-8. 용어 정리
| 용어 | 쉬운 뜻 |
|---|---|
| `HttpMethod` | GET · POST · PUT · DELETE 같은 요청 방식 |
| 역할 계층 (`RoleHierarchy`) | "ADMIN은 USER 권한도 가짐" 같은 위아래 관계 |
| 메서드 보안 | URL이 아니라 메서드 단위로 권한을 검사하는 것 |
| `@EnableMethodSecurity` | 메서드 보안 스위치. 이게 있어야 `@PreAuthorize`가 동작함 |
| `@PreAuthorize` | 메서드 실행 **전에** 조건 검사 |
| 프록시 (대리인) | 진짜 객체 앞에 서서 호출을 가로채는 객체. 스프링이 자동으로 만듦 |
| SpEL | `@PreAuthorize("...")` 따옴표 안에 쓰는 작은 식 언어 |
| IDOR | 번호만 바꿔 남의 데이터에 접근하는 취약점 |
| `@Transactional` | 메서드 안의 DB 작업을 한 묶음으로 처리함. 끝날 때 바뀐 값을 DB에 반영함 |
| `AuthenticationEntryPoint` | 로그인 안 한 사람이 거절됐을 때 응답(401)을 만드는 곳 |
| `AccessDeniedHandler` | 로그인한 사람이 권한 없어 거절됐을 때 응답(403)을 만드는 곳 |

## 3. 실행 방법과 확인 도구
4장을 시작하기 전에 한 번 읽어 둠. 4장의 단계마다 "서버 재시작 → 화면에서 누르기 → 결과 비교"를 반복함.

### 3-1. 서버와 화면 켜기
**2일차 서버가 켜져 있으면 먼저 끔** (같은 8080 포트를 씀).
```powershell
# 터미널 1 — 서버 (저장소 루트에서)
cd day03\backend
$env:JAVA_HOME = "$env:USERPROFILE\.jdks\ms-21.0.12"
.\gradlew.bat bootRun
```
```powershell
# 터미널 2 — 화면 (저장소 루트에서, npm install은 처음 한 번만)
cd day03\frontend
npm install
npm run dev
```
- IntelliJ에서 실행한다면 `SecurityDay3Application`의 ▶. 재시작은 Run 창의 🔄(Rerun)
- 서버가 뜬 신호: `Started SecurityDay3Application`

### 3-2. 재시작하면 글과 로그인이 처음으로 돌아감
- H2 메모리 DB라 **서버를 재시작하면 글이 처음 2개로 돌아옴.** 삭제 실험 뒤에는 재시작해서 되살림
- 세션도 사라지므로 재시작 뒤에는 **화면에서 다시 로그인**함 ("현재:" 표시는 화면이 기억하는 값이라 그대로 남아 있을 수 있음)

### 3-3. 화면 읽는 법
- 맨 위: 아이디 · 비밀번호, **로그인 · 로그아웃**, `현재: (로그인한 사람)`
- 가운데: 새 글 제목 칸, **글쓰기 · 새로고침 · 전체 삭제 · 결과 지우기**
- 글 목록 표: 번호 · 제목 · 작성자 · **수정 · 삭제** 버튼. 수정을 누르면 제목 입력 창이 뜸
- 맨 아래 결과표: `요청 | 상태 | 응답`. **최신 요청이 맨 위**. 글쓰기 · 수정 · 삭제 뒤에는 화면이 알아서 목록을 다시 불러서 `GET /api/posts` 줄이 하나 더 쌓임
- 로그인한 사람을 바꿀 때는 **로그아웃 → 아이디 바꾸기 → 로그인**
- 4장의 "결과"는 이 결과표에 나오는 모양 그대로 적었음. 날짜(`timestamp`)는 매번 다름

### 3-4. 화면 없이 터미널로 확인하기 (선택)
Basic으로 요청마다 사람을 바꿔 가며 볼 수 있어서 4-6 표 채우기에 편함.
```powershell
curl.exe -i http://localhost:8080/api/posts
curl.exe -i -u kim:1234 -X POST http://localhost:8080/api/posts -H "Content-Type: application/json" -d '{\"title\":\"kim 새 글\"}'
```

```java
package com.kyobo.lab;

import java.util.List;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * 3일차 · 03 (인가: 누가 무엇을 할 수 있나)
 *
 * [역할] 게시글 업무 로직 (목록 · 쓰기 · 수정 · 삭제 · 전체 삭제). 메서드 보안(@PreAuthorize)이 붙는 곳
 *
 * [알아야 할 것]
 * - 권한 검사를 컨트롤러가 아니라 여기(서비스)에 붙임. 어느 컨트롤러에서 불러도 같은 검사를 거치게 하려고
 * - @PreAuthorize는 SecurityConfig의 @EnableMethodSecurity가 있어야만 동작함. 없으면 조용히 무시됨 (4-4)
 * - 검사는 다른 빈(PostController)이 부를 때만 됨. 이 클래스 안에서 this.delete()처럼 부르면 검사가 빠짐 (가이드 1-4)
 * - update는 @Transactional이라 post.setTitle()만 해도 메서드가 끝날 때 DB에 반영됨 (save를 따로 안 부름)
 */
@Service
public class PostService {

	private final PostRepository posts;

	public PostService(PostRepository posts) {
		this.posts = posts;
	}

	public List<Post> findAll() {
		return posts.findAll();
	}

	public Post create(String title, String author) {
		return posts.save(new Post(title, author));
	}

	@Transactional // 메서드가 끝날 때 바뀐 제목을 DB에 반영함
	public Post update(Long id, String title) {
		Post post = posts.findById(id).orElseThrow(); // 없는 번호면 예외 (6장 한계)
		post.setTitle(title);
		return post;
	}

	public void delete(Long id) {
		posts.deleteById(id);
	}

	public void deleteAll() {
		posts.deleteAll();
	}
}
```

```java
package com.kyobo.lab;

import java.security.Principal;
import java.util.List;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.PutMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;

/**
 * 3일차 · 03 (인가: 누가 무엇을 할 수 있나)
 *
 * [역할] 게시판 API 5개. 같은 주소 /api/posts에 HTTP 메서드만 다른 요청들이 모여 있음
 *   - GET    /api/posts      : 목록          - POST   /api/posts      : 글쓰기
 *   - PUT    /api/posts/{id} : 제목 수정     - DELETE /api/posts/{id} : 글 하나 삭제
 *   - DELETE /api/posts      : 전체 삭제
 *
 * [알아야 할 것]
 * - 이 클래스에도 보안 코드가 없음. URL 규칙은 SecurityConfig, 메서드 규칙은 PostService에 있음
 * - 작성자는 요청 본문이 아니라 Principal(로그인 정보)에서 꺼냄. 그래서 PostRequest에 author가 없음
 * - 전체 삭제(DELETE /api/posts)는 URL 규칙을 따로 안 만듦. 메서드 보안이 막는 것을 보려고 일부러 둠 (4-4, 4-5)
 */
@RestController
@RequestMapping("/api/posts") // 이 클래스의 모든 주소 앞에 /api/posts
public class PostController {

	// 요청 본문 {"title":"..."}. author를 일부러 안 받음
	record PostRequest(String title) {
	}

	private final PostService service;

	public PostController(PostService service) {
		this.service = service;
	}

	@GetMapping
	public List<Post> list() {
		return service.findAll();
	}

	// 작성자는 요청 본문이 아니라 로그인 정보에서 정함 (남의 이름으로 글쓰기 방지)
	@PostMapping
	@ResponseStatus(HttpStatus.CREATED) // 성공하면 200 대신 201
	public Post create(@RequestBody PostRequest req, Principal principal) {
		return service.create(req.title(), principal.getName());
	}

	@PutMapping("/{id}")
	public Post update(@PathVariable Long id, @RequestBody PostRequest req) { // @PathVariable: 주소의 {id} 값
		return service.update(id, req.title());
	}

	@DeleteMapping("/{id}")
	public Map<String, Long> delete(@PathVariable Long id) {
		service.delete(id);
		return Map.of("deleted", id);
	}

	// 전체 삭제: URL 규칙에는 따로 없음. 메서드 보안이 막음 (4-4, 4-5)
	@DeleteMapping
	public Map<String, String> deleteAll() {
		service.deleteAll();
		return Map.of("deleted", "all");
	}
}
```

무엇을 위해: 같은 USER끼리 "남의 글"을 실험하려면 회원이 하나 더(kim) 있어야 하고, 처음부터 주인이 다른 글 2개가 있어야 함

무엇을 고치나 (2일차 코드 → 3일차 코드):

|---|---|---|
| 역할 주석 | `2일차 · 02` 한 줄 | 그 아래 `3일차 · 03: kim 회원과 글 2개 추가` 줄을 더하고, `[역할]` · `[알아야 할 것]`을 고침 |

```java
package com.kyobo.lab;

import org.springframework.boot.CommandLineRunner;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Component;

/**
 * 2일차 · 02 (BCrypt · DB 사용자 · 세션 로그인)
 * 3일차 · 03 (인가: 누가 무엇을 할 수 있나): kim 회원과 글 2개 추가
 *
 * [역할] 서버가 뜰 때 DB에 회원 3명(user, kim, admin)과 글 2개(1번 user의 글, 2번 kim의 글)를 넣음
 *
 * [알아야 할 것]
 * - H2 메모리 DB라 서버를 재시작하면 처음 상태(회원 3명, 글 2개)로 돌아감. 삭제 실험 뒤 되살릴 때 씀
 * - 글 번호는 넣은 순서대로 1, 2가 됨. 4장의 "1번 글 = user의 글"이 이 순서에서 나옴
 * - kim은 "같은 USER인데 남의 글"을 확인하려고 넣음
 */
@Component
public class DataInitializer implements CommandLineRunner {

	private final MemberRepository members;
	private final PostRepository posts; // ← 3일차 추가: 글을 저장하려고
	private final PasswordEncoder encoder;

	public DataInitializer(MemberRepository members, PostRepository posts, PasswordEncoder encoder) { // ← 3일차: posts 파라미터 추가
		this.members = members;
		this.posts = posts; // ← 3일차 추가
		this.encoder = encoder;
	}

	@Override
	public void run(String... args) {
		members.save(new Member("user", encoder.encode("1234"), "USER"));
		members.save(new Member("kim", encoder.encode("1234"), "USER"));   // ← 3일차 추가: 같은 USER인 다른 사람
		members.save(new Member("admin", encoder.encode("1234"), "ADMIN"));
		posts.save(new Post("user의 첫 글", "user")); // ← 3일차 추가: 1번 글 (주인 user)
		posts.save(new Post("kim의 첫 글", "kim"));   // ← 3일차 추가: 2번 글 (주인 kim)
	}
}
```

### 4-2. HTTP 메서드별 URL 규칙

> **목적**: 글 목록(GET)은 로그인 없이도 보이게, 글쓰기(POST)는 회원만 되게 함. 4-1에서 본 "로그인 안 하면 목록도 못 봄(401)"을 고침
>
> **수정**: 가져온 `SecurityConfig.java` — `authorizeHttpRequests` 안에 **두 줄 추가** + import 한 줄 추가

#### 할 일
`SecurityConfig`의 `authorizeHttpRequests` 부분에 두 줄을 추가하고, import 한 줄을 추가함. 2일차 규칙 세 줄은 그대로 둠.
```java
import org.springframework.http.HttpMethod;
```
```java
				.authorizeHttpRequests(auth -> auth
						.requestMatchers("/api/public/**").permitAll()
						// 같은 주소라도 HTTP 메서드별로 규칙을 나눔
						.requestMatchers(HttpMethod.GET, "/api/posts/**").permitAll()   // 글 읽기는 누구나
						.requestMatchers(HttpMethod.POST, "/api/posts").hasRole("USER") // 글쓰기는 ROLE_USER만
						.requestMatchers("/api/admin/**").hasRole("ADMIN")
						.anyRequest().authenticated())                                  // PUT · DELETE는 여기 걸림 (로그인만)
```
- 새 줄은 `anyRequest()`보다 **위에** 둠 (1일차와 같은 이유)
- PUT · DELETE 규칙은 일부러 안 만듦. "누구의 글인지"는 URL로 못 정하기 때문임 (1-1)

#### 확인
서버를 재시작하고 차례로 누름. 글쓰기 제목은 아무거나(예: `테스트`).

| 순서 | 로그인 | 버튼 | 상태 | 응답 |
|---|---|---|---|---|
| ① | (안 함) | 새로고침 | **200** | `[{"id":1,...,"author":"user"},{"id":2,...,"author":"kim"}]` |
| ② | (안 함) | 글쓰기 | 401 | (비어 있음) |
| ③ | user | 글쓰기 | 201 | `{"id":3,"title":"테스트","author":"user"}` |
| ④ | admin | 글쓰기 | **403** | `{"timestamp":"...","status":403,"error":"Forbidden","path":"/api/posts"}` |

- [ ] 로그인 안 해도 목록이 보임
- [ ] ④ admin인데 403 ← 관리자인데?

> `hasRole("USER")`는 "ROLE_USER를 **가진** 사람"임. admin은 ROLE_ADMIN만 있어서 거절됨. 역할 사이에는 자동으로 위아래가 없음 (1-3)

### 4-3. 역할 계층

> **목적**: 4-2에서 admin이 글쓰기 403을 받은 문제를 고침. "ADMIN은 USER가 할 수 있는 일도 모두 함"을 스프링에게 알려 줌
>
> **수정**: 가져온 `SecurityConfig.java` — **빈 메서드 하나 추가**(`roleHierarchy()`) + import 두 줄 추가. 규칙(`authorizeHttpRequests`)은 안 고침

#### 할 일

```java

	@Bean
```

### 4-6. 내 글만 수정 · 삭제 (`PostGuard`)

> **목적**: 4-1에서 kim이 user의 글을 지운 문제(IDOR)를 고침. "이 글의 작성자인가?"를 DB에서 확인해서 작성자 본인 또는 관리자만 수정 · 삭제하게 함
>
> **수정**: 빈 파일 `PostGuard.java` 새로 씀 + `PostService.java`의 `update()`, `delete()` 위에 **어노테이션 한 줄씩 추가**

#### 할 일
**`PostGuard.java`**
```java
package com.kyobo.lab;

import org.springframework.stereotype.Component;

/**
 * 3일차 · 03 (인가: 누가 무엇을 할 수 있나)
 *
 * [역할] "이 글의 작성자가 이 사람인가?"를 확인하는 소유자 검사기. @PreAuthorize 식 안에서 @postGuard로 부름
 *
 * [알아야 할 것]
 * - 빈 이름을 "postGuard"로 직접 정함. @PreAuthorize의 @postGuard와 철자가 같아야 함 (틀리면 500)
 * - URL에는 "누구의 글인지"가 없어서, DB에서 글을 꺼내 author와 비교해야만 판단 가능함 (가이드 1-1의 ③)
 * - 없는 글이면 false → 작성자가 아님으로 처리함 (관리자가 아니면 403)
 * - 화면에서 버튼을 숨기는 것과 상관없이 서버가 막음. API는 직접 부를 수 있기 때문 (가이드 1-6)
 */
@Component("postGuard") // 빈 이름을 postGuard로 정함 → @PreAuthorize("@postGuard.isAuthor(...)")
public class PostGuard {

	private final PostRepository posts;

	public PostGuard(PostRepository posts) {
		this.posts = posts;
	}

	// postId번 글의 작성자가 username이면 true
	public boolean isAuthor(Long postId, String username) {
		return posts.findById(postId)
				.map(p -> p.getAuthor().equals(username)) // 글이 있으면 작성자 비교
				.orElse(false);                           // 글이 없으면 false
	}
}
```

**`PostService.java`** — `update`, `delete` 위에 같은 어노테이션을 붙임. 완성본 전체:
```java
package com.kyobo.lab;

import java.util.List;

import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * 3일차 · 03 (인가: 누가 무엇을 할 수 있나)
 *
 * [역할] 게시글 업무 로직 (목록 · 쓰기 · 수정 · 삭제 · 전체 삭제). 메서드 보안(@PreAuthorize)이 붙는 곳
 *
 * [알아야 할 것]
 * - 권한 검사를 컨트롤러가 아니라 여기(서비스)에 붙임. 어느 컨트롤러에서 불러도 같은 검사를 거치게 하려고
 * - @PreAuthorize는 SecurityConfig의 @EnableMethodSecurity가 있어야만 동작함. 없으면 조용히 무시됨 (4-4)
 * - 검사는 다른 빈(PostController)이 부를 때만 됨. 이 클래스 안에서 this.delete()처럼 부르면 검사가 빠짐 (가이드 1-4)
 * - update는 @Transactional이라 post.setTitle()만 해도 메서드가 끝날 때 DB에 반영됨 (save를 따로 안 부름)
 */
@Service
public class PostService {

	private final PostRepository posts;

	public PostService(PostRepository posts) {
		this.posts = posts;
	}

	public List<Post> findAll() {
		return posts.findAll();
	}

	public Post create(String title, String author) {
		return posts.save(new Post(title, author));
	}

	// 작성자 본인 또는 관리자만. #id = 이 메서드의 id 파라미터, authentication.name = 로그인한 아이디
	@PreAuthorize("@postGuard.isAuthor(#id, authentication.name) or hasRole('ADMIN')")
	@Transactional // 메서드가 끝날 때 바뀐 제목을 DB에 반영함
	public Post update(Long id, String title) {
		Post post = posts.findById(id).orElseThrow(); // 없는 번호면 예외 (6장 한계)
		post.setTitle(title);
		return post;
	}

	// 작성자 본인 또는 관리자만
	@PreAuthorize("@postGuard.isAuthor(#id, authentication.name) or hasRole('ADMIN')")
	public void delete(Long id) {
		posts.deleteById(id);
	}

	// URL 규칙이 없어도 메서드에서 막음 (ADMIN만)
	@PreAuthorize("hasRole('ADMIN')")
	public void deleteAll() {
		posts.deleteAll();
	}
}
```
- 식 읽는 법은 1-5 참고. `#id`가 메서드 파라미터 이름 `id`와 같아야 함

#### 확인
한 줄(로그인 한 명)을 확인할 때마다 **서버를 재시작**함. 삭제하면 1번 글이 없어져 다음 줄 결과가 달라지기 때문임. **삭제는 각 줄의 마지막에** 함. 수정 제목은 아무거나(예: `바꿈`).

| 로그인 | 1번 글(user 작성) 수정 | 2번 글(kim 작성) 수정 | 1번 글 삭제 |
|---|---|---|---|
| user | 200 | **403** | 200 |
| kim | **403** | 200 | **403** |
| admin | 200 | 200 | 200 |

kim 줄을 예로 들면 결과표는 이렇게 쌓임 (위가 최신):
| 요청 | 상태 | 응답 |
|---|---|---|
| `DELETE /api/posts/1` | 403 | `{"timestamp":"...","status":403,"error":"Forbidden","path":"/api/posts/1"}` |
| `PUT /api/posts/2` | 200 | `{"id":2,"title":"바꿈","author":"kim"}` |
| `PUT /api/posts/1` | 403 | `{"timestamp":"...","status":403,"error":"Forbidden","path":"/api/posts/1"}` |

- [ ] 세 줄 모두 위 표대로 나옴
- [ ] kim이 1번 글 수정에 실패한 뒤 목록을 보면 1번 제목이 **그대로**(`user의 첫 글`)임

### 4-7. 401 · 403 응답을 JSON 한 모양으로

> **목적**: 지금 401은 본문이 비어 있고 403은 스프링 기본 에러 모양이라 화면에서 다루기 불편함. 어디서 거절됐든 `{"error":"..."}` 한 모양으로 맞춤 (1-7)
>
> **수정**: 가져온 `SecurityConfig.java` — `.exceptionHandling(...)` **블록 추가** + `json(...)` **메서드 추가** + import 두 줄 + 역할 주석에 3일차 줄 추가. 오늘 `SecurityConfig`를 고치는 마지막 단계라 완성본 전체도 같이 둠

#### 할 일
**① 바꾸기 전 응답을 먼저 봄** (4-6 상태 그대로):
| 상황 | 요청 | 상태 | 응답 |
|---|---|---|---|
| 로그아웃 상태로 글쓰기 | `POST /api/posts` | 401 | (비어 있음) |
| kim으로 1번 글 삭제 | `DELETE /api/posts/1` | 403 | `{"timestamp":"...","status":403,"error":"Forbidden","path":"/api/posts/1"}` |

모양이 제각각임 (1-7).

**② `SecurityConfig`에 추가할 것 네 군데**

(가) import 두 줄
```java
import java.io.IOException;
import jakarta.servlet.http.HttpServletResponse;
```

(나) `.authorizeHttpRequests(...)` 블록이 끝나는 줄(`.anyRequest().authenticated())`) **바로 아래**에 블록 추가
```java
						.anyRequest().authenticated())                                  // (여기까지 기존 코드)
				// 401 · 403을 JSON 한 모양으로 돌려줌. ExceptionTranslationFilter가 이 두 처리기를 부름
				.exceptionHandling(ex -> ex
						.authenticationEntryPoint((req, res, e) -> json(res, 401, "로그인이 필요합니다")) // 로그인 안 한 사람
						.accessDeniedHandler((req, res, e) -> json(res, 403, "권한이 없습니다")))         // 로그인했지만 권한 없음
				.httpBasic(Customizer.withDefaults())                                   // (여기부터 기존 코드)
```

(다) `filterChain()` 메서드 아래에 메서드 추가
```java
	// 상태 코드와 {"error":"..."} 본문을 직접 써서 응답함
	private static void json(HttpServletResponse res, int status, String message) throws IOException {
		res.setStatus(status);
		res.setContentType("application/json;charset=UTF-8"); // charset이 없으면 한글이 깨짐
		res.getWriter().write("{\"error\":\"" + message + "\"}");
	}
```

(라) 역할 주석 맨 위 `2일차 · 02 ...` 줄 아래에 한 줄 추가하고, `[역할]` · `[알아야 할 것]`을 아래 완성본처럼 고침
```
 * 3일차 · 03 (인가: 누가 무엇을 할 수 있나): HTTP 메서드별 규칙, 역할 계층, 메서드 보안 스위치, 401·403 JSON 응답
```

**③ 완성본 전체** — 내 파일과 비교해 봄. 오늘 추가한 곳에는 `(4-N)`을 붙여 둠
```java
package com.kyobo.lab;

import java.io.IOException;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.access.hierarchicalroles.RoleHierarchy;
import org.springframework.security.access.hierarchicalroles.RoleHierarchyImpl;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;

import jakarta.servlet.http.HttpServletResponse;

/**
 * 1일차 · 01 (스프링 시큐리티 시작)
 * 2일차 · 02 (BCrypt · DB 사용자 · 세션 로그인): PasswordEncoder 추가, 메모리 사용자 삭제, CSRF 끔, 폼 로그인을 React용으로 바꿈
 * 3일차 · 03 (인가: 누가 무엇을 할 수 있나): HTTP 메서드별 규칙, 역할 계층, 메서드 보안 스위치, 401·403 JSON 응답
 *
 * [역할] 보안 설정의 중심. 스프링 시큐리티에게 알려 주는 것
 *   1. 주소 + HTTP 메서드별 규칙 (문 앞 검사)            → filterChain()
 *   2. 거절됐을 때 응답 모양 (401 · 403 JSON)              → filterChain()의 exceptionHandling
 *   3. 로그인 방식 (HTTP Basic, 세션 로그인, 로그아웃)       → filterChain()
 *   4. 역할 계층 (ADMIN > USER), 비밀번호 비교 (BCrypt)      → roleHierarchy(), passwordEncoder()
 *   5. 메서드 보안 켜기 (@PreAuthorize 동작)                → @EnableMethodSecurity
 *
 * [알아야 할 것]
 * - URL 규칙은 "누구의 글인지"를 모름. 소유자 검사는 PostService의 @PreAuthorize + PostGuard가 함
 * - @EnableMethodSecurity가 빠지면 @PreAuthorize가 전부 조용히 무시됨. 에러도 경고도 없음 (4-4)
 * - exceptionHandling의 두 처리기는 URL 규칙 거절과 메서드 보안 거절을 모두 같은 모양으로 바꿈
 * - CSRF는 아직 꺼 둠. 4일차에 토큰 방식으로 다시 켬
 */
@Configuration
@EnableMethodSecurity // (4-5) 메서드 보안 스위치: @PreAuthorize가 붙은 빈을 대리인(프록시)으로 감싸 검사하게 함
public class SecurityConfig {

	@Bean
	public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
		http
				.cors(Customizer.withDefaults())
				.csrf(csrf -> csrf.disable()) // 4일차에 토큰 방식으로 다시 켬
				.authorizeHttpRequests(auth -> auth
						.requestMatchers("/api/public/**").permitAll()
						// (4-2) 같은 주소라도 HTTP 메서드별로 규칙을 나눔
						.requestMatchers(HttpMethod.GET, "/api/posts/**").permitAll()   // (4-2) 글 읽기는 누구나
						.requestMatchers(HttpMethod.POST, "/api/posts").hasRole("USER") // (4-2) 글쓰기는 ROLE_USER만 (역할 계층으로 ADMIN도)
						.requestMatchers("/api/admin/**").hasRole("ADMIN")
						.anyRequest().authenticated())                                  // PUT · DELETE는 여기 걸림 (로그인만)
				// (4-7) 401 · 403을 JSON 한 모양으로 돌려줌. ExceptionTranslationFilter가 이 두 처리기를 부름
				.exceptionHandling(ex -> ex
						.authenticationEntryPoint((req, res, e) -> json(res, 401, "로그인이 필요합니다")) // 로그인 안 한 사람
						.accessDeniedHandler((req, res, e) -> json(res, 403, "권한이 없습니다")))         // 로그인했지만 권한 없음
				.httpBasic(Customizer.withDefaults())
				.formLogin(form -> form
						.loginProcessingUrl("/api/login")
						.successHandler((req, res, auth) -> res.setStatus(200))
						.failureHandler((req, res, e) -> res.setStatus(401)))
				.logout(logout -> logout
						.logoutUrl("/api/logout")
						.logoutSuccessHandler((req, res, auth) -> res.setStatus(200)));
		return http.build();
	}

	// (4-7) 상태 코드와 {"error":"..."} 본문을 직접 써서 응답함
	private static void json(HttpServletResponse res, int status, String message) throws IOException {
		res.setStatus(status);
		res.setContentType("application/json;charset=UTF-8"); // charset이 없으면 한글이 깨짐
		res.getWriter().write("{\"error\":\"" + message + "\"}");
	}

	// (4-3) 역할 계층: ADMIN은 USER가 할 수 있는 일도 모두 함. URL 규칙과 메서드 보안 둘 다 이 빈을 씀
	@Bean
	static RoleHierarchy roleHierarchy() { // static: 보안 설정이 만들어지기 전에 먼저 필요해서 붙임
		return RoleHierarchyImpl.fromHierarchy("ROLE_ADMIN > ROLE_USER"); // 여기서는 ROLE_까지 다 씀
	}

	// 비밀번호를 BCrypt 해시로 만들고 비교함 (2일차)
	@Bean
	public PasswordEncoder passwordEncoder() {
		return new BCryptPasswordEncoder();
	}
}
```
- `(req, res, e) -> json(...)`: 거절될 때마다 실행할 코드. 1일차에 본 **AuthenticationEntryPoint(401)**와 **AccessDeniedHandler(403)**를 직접 바꾼 것임 (1-7)
- 새로 추가한 import: `java.io.IOException`, `jakarta.servlet.http.HttpServletResponse`

#### 확인
서버를 재시작하고 ①과 같은 상황을 다시 만듦.

| 상황 | 요청 | 상태 | 응답 | 거절한 곳 |

### 4-8. 보안 로그 `TRACE`로 거절 위치 구분

> **목적**: 같은 403이라도 "문 앞(URL 규칙 필터)"에서 거절됐는지 "방 안(메서드 보안)"에서 거절됐는지 로그로 구분함
>
> **수정**: `application.properties` — **로그 설정 한 줄 추가** (코드는 안 고침)

#### 할 일
`application.properties`를 아래로 바꿈.
```properties
spring.application.name=security-day3

# 인가 판정(URL 규칙 · 메서드 보안)이 어디서 일어나는지 로그로 봄
logging.level.org.springframework.security=TRACE
```

#### 확인
서버를 재시작하고 두 가지를 누른 뒤 로그를 봄.

**① 로그아웃 상태로 글쓰기** → `Securing POST /api/posts` 아래:
```
Checking authorization on POST /api/posts using AuthorityAuthorizationManager[authorities=[ROLE_USER]]
```

**② `kim`으로 로그인 → 1번 글 수정** → `Securing PUT /api/posts/1` 아래:
```
Secured PUT /api/posts/1
Authorizing method invocation ReflectiveMethodInvocation: public com.kyobo.lab.Post com.kyobo.lab.PostService.update(java.lang.Long,java.lang.String); ...
Failed to authorize ReflectiveMethodInvocation: public com.kyobo.lab.Post com.kyobo.lab.PostService.update(java.lang.Long,java.lang.String); ...
AuthorizationDeniedException: Access Denied
```

**③ 표를 채움**

| 질문 | 내 답 |
|---|---|
| ①을 거절한 곳은 필터인가, 메서드인가? | |
| ②에서 `Secured PUT`은 무슨 뜻인가? | |
| ②를 거절한 곳은? 그 뒤 403으로 바꾼 필터는? | |
| ②를 URL 규칙만으로 막을 수 있을까? | |

<details>
<summary>정답 보기</summary>

1. 필터 — `AuthorizationFilter`가 URL 규칙(`ROLE_USER` 필요)으로 거절함. 컨트롤러까지 가지 않음
2. URL 규칙은 통과했다는 뜻 — PUT은 `anyRequest().authenticated()`라 로그인만 하면 통과
3. `PostService.update`의 `@PreAuthorize`가 거절(`AuthorizationDeniedException`) → `ExceptionTranslationFilter`가 받아서 403(우리가 만든 `accessDeniedHandler`)으로 바꿈
4. 없음 — URL에는 "누구의 글인지"가 없음. 글을 DB에서 찾아 작성자와 비교해야 하므로 메서드(데이터) 단계에서만 가능 (1-1)

</details>

- 로그가 너무 많으면 확인 후 `TRACE`를 `DEBUG`로 바꿈. IntelliJ 실행 창에서 `Ctrl + F`로 `Secured PUT` 검색

## 6. 알려진 한계 (면접에서 물어볼 만한 부분)
1. **CSRF 보호가 아직 꺼져 있음**
   - 세션 로그인 + 글 삭제(DELETE)가 생겼으니 CSRF 공격의 피해가 더 커짐 → 4일차에 다시 켬
2. **같은 클래스 안에서 부르면 메서드 보안이 빠짐 (자기 호출)**
   - 프록시가 바깥 호출만 가로채기 때문 (1-4). 예: `PostService` 안의 다른 메서드가 `this.deleteAll()`을 부르면 검사 없이 실행됨 → 보안 메서드는 바깥에서만 부르게 설계함
3. **없는 글을 다루면 응답이 들쭉날쭉함**
   - `kim`이 없는 99번 글을 삭제하면 `403`(작성자가 아님), `admin`이 99번 글을 수정하면 `500`(`orElseThrow()` 예외) → 원래는 `404 Not Found`가 맞음. 예외를 상태 코드로 바꾸는 처리(`@ExceptionHandler` 등)가 필요함
4. **JSON을 문자열 이어 붙이기로 만듦**
   - 메시지에 `"`가 들어가면 JSON이 깨짐. 지금은 고정 문구라 괜찮지만, 실제는 `ObjectMapper`로 만듦
5. **소유자 검사를 위해 DB를 한 번 더 읽음**
   - `PostGuard`가 글을 읽고, `update`가 또 읽음. 요청이 많으면 부담이 되고, 두 번 읽는 사이에 데이터가 바뀔 수도 있음 → 서비스 안에서 한 번 읽고 바로 검사하는 방식도 있음
6. **역할이 문자열 하나뿐임**
   - "게시판 관리자는 글만 지울 수 있고 회원 목록은 못 봄" 같은 세밀한 권한은 못 나눔 → 권한(authority)을 역할과 따로 두는 방식이 필요함
7. **화면은 권한과 상관없이 모든 버튼을 보여 줌**
   - 보안은 서버가 했으니 맞지만, 사용성은 나쁨. 화면은 "보여 줄지"만, 서버는 "해도 되는지"를 정함 (둘 다 필요함)
