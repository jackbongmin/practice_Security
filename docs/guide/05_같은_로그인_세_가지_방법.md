# 가이드 05 · 같은 로그인, 세 가지 방법 (세션 · 쿠키 · 토큰)

> **한 줄 요약**: 4일차 서버에 로그인 방법을 두 개 더 붙여 **로그인 상태를 어디에 두느냐**만 다른 세 방식을 나란히 비교함. ① 서버 메모리에 두는 **세션**, ② 브라우저 쿠키에 아이디만 두는 **순진한 쿠키**(일부러 뚫림), ③ 브라우저가 **서명된 토큰(JWT)**을 들고 다니는 방식

## 목표
- 세션 로그인은 **서버를 재시작하면 풀린다**는 것을 보고, 그 이유(상태가 서버 메모리에 있음)를 설명할 수 있음
- 쿠키에 아이디만 두면 **쿠키 값을 `admin`으로 바꾸는 것만으로 관리자가 되는** 것을 직접 봄
- 아이디 · 비밀번호를 확인하고 **서명한 JWT를 발급**함. 토큰 안의 내용은 **누구나 읽을 수 있다**는 것을 확인함
- `/api/token/**`만 맡는 **두 번째 보안 필터 체인**을 만들어 토큰을 검사함. 내용을 바꾼 토큰은 **서명이 안 맞아 401**
- 토큰의 `roles`를 스프링 권한(`ROLE_ADMIN`)으로 바꿔 관리자 API를 지킴
- 세션과 토큰을 **재시작 · 만료 · 로그아웃** 세 가지로 비교해 표를 채움

## 완료 기준
| 확인 | 오늘 시작할 때 | 오늘 끝났을 때 |
|---|---|---|
| ① 세션 로그인 → 서버 재시작 → 내 정보 | `401` | 그대로 `401` (세션의 성질. 4-1에서 봄) |
| ② 순진한 쿠키 로그인 | `401` (API 없음) | `200 {"username":"user"}` + 쿠키 `naive_user=user` |
| ② 쿠키를 `admin`으로 바꾸고 내 정보 | — | `{"username":"admin","isAdmin":true}` ← **비밀번호 없이 관리자** (일부러) |
| ③ 토큰 로그인 | `403` `CSRF 토큰이 없거나 틀립니다.` | `200 {"token":"eyJ..."}`, `Set-Cookie` 없음 |
| ③ 토큰으로 내 정보 / 토큰 없이 | — | `200 {"username":"user","roles":["USER"],...}` / `401` |
| ③ 내용을 `admin`으로 바꾼 위조 토큰 | — | `401` `Invalid signature` |
| ③ 관리자 API (user 토큰 / admin 토큰) | — | `403` / `200 {"secret":"관리자 전용 데이터"}` |
| ③ 토큰 로그인 → 서버 재시작 → 내 정보 | — | `200` ← 세션과 다름 |

- [ ] 5일차 원본 테스트 7개가 확인하는 내용(쿠키 조작 · 쿠키 로그인 CSRF · 토큰 내 정보 · 토큰 없음 401 · 위조 401 · 관리자 · 틀린 비밀번호)이 위 표와 같음 (Claude Code가 가이드 코드로 7개 통과 확인함)

## 만들 API
| 요청 | 설명 | 누가 쓸 수 있나 |
|---|---|---|
| `POST /api/public/naive/login` | 순진한 쿠키 로그인. 본문 JSON `{"username","password"}` → 쿠키 `naive_user=아이디` | 누구나 (CSRF 토큰 필요) |
| `GET /api/public/naive/me` | 쿠키 `naive_user` 값을 **그대로 믿고** 돌려줌 | 누구나 |
| `POST /api/token/login` | 토큰 로그인. 본문 JSON → `{"token":"eyJ..."}` | 누구나 (CSRF 토큰 **필요 없음**) |
| `GET /api/token/me` | 토큰에서 꺼낸 정보 | 토큰 있는 사람 |
| `GET /api/token/admin` | 관리자 전용 데이터 | ADMIN 토큰 |
| 4일차 API | 세션 로그인 · 로그아웃 · 내 정보 · CSRF 토큰 · 게시판 등 | 4일차와 같음 |

응답 예시:
```json
// POST /api/token/login   {"username":"user","password":"1234"}
{"token": "eyJhbGciOiJIUzI1NiJ9.eyJpc3MiOiJzZWN1cml0eS1kYXk1Iiwic3ViIjoidXNlciIs...lJwM3qThfJ2qsauIk2zZyIEH2lkU6KLBrZBZvXhi26I"}
// GET /api/token/me   (Authorization: Bearer eyJ...)
{"username": "user", "roles": ["USER"], "expiresAt": "2026-11-09T02:02:27Z"}
// GET /api/public/naive/me   (쿠키 naive_user=admin)
{"username": "admin", "isAdmin": true}
```
- 계정: `user` · `kim`(USER), `admin`(ADMIN). 비밀번호는 모두 `1234`
- JSON의 **키 순서는 서버를 켤 때마다 바뀔 수 있음** (`Map.of`의 성질). 순서가 달라도 정상

## 1. 개념 먼저

### 1-1. 오늘의 질문: "이 요청을 보낸 사람이 누구지?"
HTTP는 요청 하나하나가 **서로 모르는** 방식임(무상태, stateless). 로그인을 한 번 했으면 다음 요청에서도 "아까 로그인한 그 사람"임을 알려 줘야 함. 그 증거를 **어디에 두느냐**로 세 방식이 나뉨.

| 방식 | 비유 | 로그인 상태가 있는 곳 | 요청마다 브라우저가 내는 것 |
|---|---|---|---|
| ① 세션 | 옷 보관소 번호표 | **서버 메모리** (번호표 → 사람 장부) | 쿠키 `JSESSIONID=번호` (자동) |
| ② 순진한 쿠키 | 손으로 쓴 이름표 | **브라우저 쿠키**에 아이디 그대로 | 쿠키 `naive_user=user` (자동) |
| ③ 토큰 (JWT) | 도장 찍힌 신분증 | **브라우저가 가진 토큰** (서버는 저장 안 함) | 헤더 `Authorization: Bearer eyJ...` (화면이 직접 실음) |

- ① 서버가 장부를 가지고 있으니 **서버가 꺼지면 장부도 사라짐**(4-1). 서버가 여러 대면 다른 서버는 이 장부를 모름
- ② 이름표는 누구나 고쳐 쓸 수 있음. 서버가 이름표를 **확인 없이 믿으면** 끝남(4-2)
- ③ 신분증에는 **서버만 가진 도장(서명)**이 찍혀 있음. 내용을 고치면 도장이 안 맞음(4-4). 서버는 장부 없이 **도장만 보고** 믿음 → 재시작해도 그대로(4-6)

### 1-2. JWT 생김새: 점(`.`)으로 나뉜 세 조각
```
eyJhbGciOiJIUzI1NiJ9 . eyJpc3MiOiJzZWN1cml0eS1kYXk1Iiwic3ViIjoidXNlciIs... . lJwM3qThfJ2qsauIk2zZyIEH2lkU6KLBrZBZvXhi26I
      헤더                              내용 (payload)                                     서명
{"alg":"HS256"}     {"iss":"security-day5","sub":"user","exp":...,"iat":...,"roles":["USER"]}   HMAC-SHA256(헤더.내용, 서버 키)
```
- **헤더 · 내용은 Base64URL로 바꾼 글자일 뿐 암호화가 아님.** 누구나 되돌려 읽을 수 있음 → 비밀번호 · 개인정보를 넣지 않음
- **서명** = 헤더와 내용을 **서버의 비밀 키**로 섞어 만든 값. 키가 없으면 만들 수 없음. 내용을 한 글자라도 바꾸면 서명이 안 맞음
- 오늘 쓰는 서명 방식 **HS256**은 만드는 키와 검사하는 키가 **같은 키 하나**임 (대칭 키). 그래서 `JwtConfig`가 그 키 하나로 인코더 · 디코더를 둘 다 만듦
- 내용에 들어가는 이름(클레임, claim)

| 클레임 | 뜻 | 오늘 값 |
|---|---|---|
| `iss` (issuer) | 누가 발급했나 | `security-day5` |
| `sub` (subject) | 누구의 토큰인가 | `user` |
| `iat` (issued at) | 언제 발급했나 (1970년부터 초) | `1794189147` |
| `exp` (expires) | 언제까지 쓸 수 있나 | `iat + 600` (10분) |
| `roles` | 무슨 역할인가 (우리가 정한 이름) | `["USER"]` |

### 1-3. 토큰을 쓰면 CSRF 걱정이 없는 이유
- 4일차 CSRF 공격은 "브라우저가 **쿠키를 자동으로** 실어 준다"에서 시작했음
- 토큰은 쿠키가 아니라 **화면(JavaScript)이 직접** `Authorization` 헤더에 실음. 공격자 사이트의 폼은 이 헤더를 붙일 수 없음
- 그래서 토큰 체인에서는 `csrf.disable()`을 해도 안전함. 대신 **토큰을 어디에 보관하느냐**가 새 숙제가 됨 (6장 한계)
- 오늘 화면은 토큰을 **React 상태(메모리)**에만 둠 → 새로고침하면 사라짐

### 1-4. 보안 필터 체인이 두 개
1일차에 "요청마다 **처음 맞는 체인 하나**만 쓴다"고 했음. 오늘 처음으로 체인이 두 개가 됨.
```
요청 ─┬─ /api/token/** 인가?  ── 예 ─→ tokenChain (@Order(1))  : 토큰 검사, CSRF 끔, 세션 안 만듦
      └─ 아니오 ────────────────────→ filterChain (4일차 SecurityConfig) : 세션 · CSRF · Basic · 폼 로그인
```
- `securityMatcher("/api/token/**")`: 이 체인이 **맡을 주소**. 이 줄이 없으면 모든 요청을 이 체인이 가져가서 세션 로그인이 망가짐
- `@Order(1)`: 숫자가 작을수록 먼저 검사함. 4일차 체인은 순서가 없어서 맨 뒤
- `SessionCreationPolicy.STATELESS`: 이 체인은 세션을 **만들지도 쓰지도 않음** → 응답에 `Set-Cookie`가 없음
- `oauth2ResourceServer(oauth -> oauth.jwt(...))`: 요청의 `Authorization: Bearer ...`를 꺼내 `JwtDecoder`로 **서명 · 만료를 검사**하는 필터(`BearerTokenAuthenticationFilter`)를 켬

### 1-5. 토큰의 역할 → 스프링 권한
- `hasRole("ADMIN")`은 권한 목록에 **`ROLE_ADMIN`**이 있는지 봄 (3일차)
- 그런데 토큰 검사 필터의 **기본 변환기**는 `scope`(또는 `scp`) 클레임을 읽어 `SCOPE_xxx` 권한을 만듦. 우리 토큰에는 `scope`가 없고 `roles`가 있음 → 권한이 **하나도 안 생김** → admin도 403 (4-5에서 직접 봄)
- 그래서 `rolesConverter()`로 "`roles` 클레임을 읽고, 앞에 `ROLE_`을 붙여라"라고 알려 줌 → `["ADMIN"]` → `ROLE_ADMIN`

### 1-6. 만료와 로그아웃
- 서버는 토큰을 저장하지 않으므로 **"이 토큰 이제 무효"라고 지울 곳이 없음.** 로그아웃 = 화면이 토큰을 **버리는 것**뿐. 누가 복사해 둔 토큰은 `exp`까지 유효함
- 그래서 토큰은 **수명(`exp`)을 짧게** 줌. 오늘은 600초(10분)
- 검사할 때 **시계 차이 허용(clock skew) 60초**가 기본으로 있음 → 5초짜리 토큰도 약 65초까지는 통과함 (4-6에서 봄)
- 세션은 반대로 서버가 장부에서 지우면 **그 즉시** 무효

### 1-7. 용어 정리
| 용어 | 쉬운 뜻 |
|---|---|
| 무상태 (stateless) | 서버가 요청 사이에 아무것도 기억하지 않는 것 |
| 세션 | 서버 메모리에 둔 "번호표 → 로그인한 사람" 장부 |
| JWT (JSON Web Token) | `헤더.내용.서명` 세 조각으로 된 토큰. 내용은 누구나 읽고, 서명은 서버만 만듦 |
| 클레임 (claim) | 토큰 내용에 든 항목 하나 (`sub`, `exp`, `roles` …) |
| Base64URL | 글자를 URL에 써도 되는 글자로 바꾸는 방법. **암호화 아님** |
| 서명 · HS256 | 비밀 키로 만든 "고치지 않았다"는 증명. HS256은 키 하나로 만들고 검사함 |
| Bearer 토큰 | "가진 사람이 주인"인 토큰. `Authorization: Bearer <토큰>` 헤더로 보냄 |
| `JwtEncoder` / `JwtDecoder` | 토큰 만들기(서명) / 검사하기(서명 · 만료) |
| 리소스 서버 | 토큰을 받아 검사하고 API를 내주는 서버. `oauth2ResourceServer()`가 그 기능을 켬 |
| `securityMatcher` | 이 보안 필터 체인이 맡을 주소 |
| `STATELESS` | 세션을 만들지도 쓰지도 않는 설정 |
| `AuthenticationManager` | 아이디 · 비밀번호를 확인해 주는 스프링 시큐리티 부품. 2일차 `JpaUserDetailsService` + BCrypt를 씀 |

## 2. 미리 바꿔둔 설정
### 2-1. 4일차에서 가져온 파일
5일차는 **4일차 완성 코드에 파일 세 개를 더하는 날**임. 그래서 내가 쓴 `day04` 백엔드를 `day05`로 미리 복사해 둠.

| 파일 | 상태 | 오늘 할 일 |
|---|---|---|
| `SecurityConfig` · `WebConfig` · `ApiController` · `CsrfController` · `Member` · `MemberController` · `MemberRepository` · `JpaUserDetailsService` · `Post*` · `DataInitializer` | 4일차 코드 그대로 | **안 고침** |
| `SecurityDay5Application` | 4일차 것에서 **이름만 바꿔** 만들어 둠 | 안 고침 |
| `NaiveCookieController` | **빈 파일** (역할 주석만) | **새로 씀**: 4-2 |
| `JwtConfig` | **빈 파일** (역할 주석만) | **새로 씀**: 4-3 → 4-4 · 4-5에서 늘림 |
| `TokenController` | **빈 파일** (역할 주석만) | **새로 씀**: 4-3 → 4-4 · 4-5에서 늘림 |

- 오늘 `SecurityConfig`는 **한 줄도 안 고침.** 토큰 방식은 `JwtConfig`에 **체인을 따로** 만들어서 붙임 (1-4)
- 내 4일차 `SecurityConfig`에는 4-9의 CSP `.headers(...)` 블록이 없고, 거절 메시지 끝에 마침표가 있음(`CSRF 토큰이 없거나 틀립니다.`). 오늘 내용과는 상관없음. 이 가이드의 결과는 **내 코드 그대로** 돌려 받은 값이라 마침표가 붙어 있음
- 4일차 폴더(`day04`)는 그대로 남아 있음

### 2-2. 설정 파일
- `build.gradle`: 의존성 **한 줄 추가함** — JWT 만들기 · 검사하기와 토큰 검사 필터가 들어 있음
  ```groovy
  implementation 'org.springframework.boot:spring-boot-starter-oauth2-resource-server'
  ```
  - 이 줄만 있고 `JwtConfig`가 비어 있으면 아무 일도 안 함 (오늘 시작 상태에서 4일차와 똑같이 동작하는 것을 Claude Code가 확인함)
- `application.properties`: 서명 키와 토큰 수명 **두 줄 추가함**
  ```properties
  spring.application.name=security-day5

  # 5일차: JWT 서명 키(HS256은 32바이트 이상)와 토큰 유효 시간(초). 4-6에서 ttl을 잠깐 5로 바꿈
  jwt.secret=day5-practice-secret-key-change-me-0123456789
  jwt.ttl-seconds=600
  ```
  - 키는 실습용이라 파일에 적었음. 운영에서는 **환경 변수나 비밀 저장소**에 둠 (6장)
  - 4-6에서 `jwt.ttl-seconds`를 **잠깐 `5`로 바꿨다가 되돌림** (바꾸기 전후 차이를 보는 실습이라 직접 함)
- `settings.gradle`: 프로젝트 이름이 `security-day5`

### 2-3. 화면 (`day05/frontend`)
4일차 게시판 화면이 아니라 **세 방식 버튼이 있는 새 화면**임. 오늘은 고치지 않음.

| 줄 | 버튼 | 보내는 요청 |
|---|---|---|
| ① 세션 | 로그인 · 내 정보 · 로그아웃 | `POST /api/login`(CSRF 토큰 실음) · `GET /api/me` · `POST /api/logout`. 쿠키 자동 |
| ② 순진한 쿠키 | 로그인 · 내 정보 | `POST /api/public/naive/login`(CSRF 토큰 실음) · `GET /api/public/naive/me`. 쿠키 자동 |
| ③ 토큰(JWT) | 로그인 · 내 정보 · 관리자 API · 로그아웃(토큰 버리기) | `POST /api/token/login` · `GET /api/token/me` · `GET /api/token/admin`. **쿠키 안 보냄**, `Authorization: Bearer` 헤더 |

- ③ 줄 아래에 **토큰**과 **내용(payload)**(가운데 조각을 화면이 Base64URL로 풀어 보여 줌)이 나옴
- "로그아웃(토큰 버리기)"는 **서버에 요청을 안 보냄.** 화면이 들고 있던 토큰을 지울 뿐 (1-6)

### 3-5. 터미널로 확인하기 (선택)
- 토큰 API는 **CSRF 토큰이 필요 없음** (토큰 체인은 CSRF를 끔). 그래서 curl로 바로 보낼 수 있음
```powershell
# 토큰 받기 → $t에 저장
$t = (Invoke-RestMethod -Method Post http://localhost:8080/api/token/login -ContentType "application/json" -Body '{"username":"user","password":"1234"}').token

# 토큰으로 내 정보
curl.exe -i http://localhost:8080/api/token/me -H "Authorization: Bearer $t"
```
- `Invoke-RestMethod`: PowerShell에 들어 있는 요청 명령. JSON 응답을 알아서 풀어 줘서 `.token`으로 꺼낼 수 있음
- 세션 · 순진한 쿠키 로그인은 **CSRF 토큰이 필요**해서 curl로 하기 번거로움 → 화면에서 함 (4일차 3-5)

### 4-2. 순진한 쿠키 로그인 (일부러 뚫리는 코드)

> **목적**: "서버에 두지 말고 **쿠키에 아이디를 넣어 두면** 재시작해도 안 풀리지 않을까?" → 그렇게 만들면 무슨 일이 생기는지 봄 (1-1 ②). **실제로 쓰면 안 되는 코드**임
>
> **수정**: 빈 파일 `NaiveCookieController.java` 새로 씀

#### 할 일 전에: 지금 상태
② 순진한 쿠키 줄에서 **내 정보**
| 요청 | 상태 | 응답 |
|---|---|---|
| `[쿠키] GET /api/public/naive/me` | 401 | `{"error":"로그인이 필요합니다"}` |

- `/api/public/**`는 누구나 들어올 수 있는데 401인 이유: 주소를 맡을 컨트롤러가 없어서 404가 나고, 404를 보여 주는 `/error` 주소가 `anyRequest().authenticated()`에 걸림 (3일차와 같은 현상)

#### 할 일
`NaiveCookieController.java` — 완성본 전체
```java
package com.kyobo.lab;

import java.util.Map;

import org.springframework.http.HttpHeaders;
import org.springframework.http.ResponseCookie;
import org.springframework.http.ResponseEntity;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.core.AuthenticationException;
import org.springframework.web.bind.annotation.CookieValue;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

/**
 * 5일차 · 05 (같은 로그인, 세 가지 방법)
 *
 * [역할] 일부러 잘못 만든 "쿠키에 아이디만 저장하는" 로그인. 세션 · 토큰과 비교하려고 만듦 (실제로 쓰면 안 됨)
 *   - POST /api/public/naive/login : 아이디 · 비밀번호를 확인하고 쿠키 naive_user=아이디 를 내려 줌
 *   - GET  /api/public/naive/me    : 쿠키 naive_user 값을 그대로 믿고 "누구인지" 돌려줌
 *
 * [알아야 할 것]
 * - 브라우저에 둔 값은 사용자가 마음대로 바꿀 수 있음. 서버가 그 값을 확인 없이 믿는 것이 이 클래스의 구멍 (가이드 4-2)
 * - 주소가 /api/public/** 라서 SecurityConfig 규칙상 누구나 부를 수 있음. 로그인 여부는 이 클래스가 쿠키로 "직접" 판단함
 * - 로그인 POST는 4일차 CSRF 보호에 걸림 → 화면은 X-CSRF-TOKEN 헤더를 실어 보냄
 * - 비밀번호 확인은 직접 하지 않고 스프링 시큐리티의 AuthenticationManager에게 맡김 (JpaUserDetailsService + BCrypt)
 */
@RestController
public class NaiveCookieController {

    // 로그인 요청 본문 {"username":"user","password":"1234"}을 담는 그릇
    record LoginRequest(String username, String password) {
    }

    // AuthenticationManager를 꺼내 주는 스프링 시큐리티 부품. 우리 사용자(DB) + BCrypt로 확인하는 관리자를 줌
    private final AuthenticationConfiguration authConfig;

    public NaiveCookieController(AuthenticationConfiguration authConfig) {
        this.authConfig = authConfig;
    }

    @PostMapping("/api/public/naive/login")
    public ResponseEntity<Map<String, String>> login(@RequestBody LoginRequest req) throws Exception {
        try {
            // 아이디 · 비밀번호 확인. 틀리면 AuthenticationException을 던짐 (2일차 폼 로그인이 하던 일을 직접 부름)
            authConfig.getAuthenticationManager().authenticate(
                    new UsernamePasswordAuthenticationToken(req.username(), req.password()));
        } catch (AuthenticationException e) {
            return ResponseEntity.status(401).body(Map.of("error", "아이디 또는 비밀번호가 틀립니다"));
        }
        // 구멍: 쿠키에 아이디를 "그대로" 넣음. 서명도 암호화도 없음
        ResponseCookie cookie = ResponseCookie.from("naive_user", req.username()).path("/").build();
        return ResponseEntity.ok()
                .header(HttpHeaders.SET_COOKIE, cookie.toString()) // 응답 헤더 Set-Cookie: naive_user=user; Path=/
                .body(Map.of("username", req.username()));
    }

    @GetMapping("/api/public/naive/me")
    public Map<String, Object> me(@CookieValue(name = "naive_user", required = false) String username) { // 요청의 쿠키 값을 꺼냄. 없으면 null
        if (username == null) {
            return Map.of("username", "(쿠키 없음)");
        }
        // 구멍: 쿠키 값이 진짜 로그인한 사람인지 확인하지 않고 그대로 믿음
        return Map.of("username", username, "isAdmin", username.equals("admin"));
    }
}
```
- `AuthenticationConfiguration`: 스프링 시큐리티가 만들어 둔 `AuthenticationManager`를 꺼내 주는 부품. 여기서 꺼낸 관리자는 2일차 `JpaUserDetailsService`(DB 사용자)와 `PasswordEncoder`(BCrypt)로 비밀번호를 확인함. 4-3의 `TokenController`도 똑같이 씀
- `ResponseCookie`: `Set-Cookie` 헤더 값을 만들어 주는 도구. `.path("/")`는 "이 서버의 모든 주소로 갈 때 이 쿠키를 실어라"
- `HttpOnly`를 안 붙였음 → 스크립트(`document.cookie`)로도 읽고 고칠 수 있음 (할 일 ③에서 씀)

#### 확인 ①: 로그인
서버를 재시작하고 ② **로그인** → **내 정보**
| 요청 | 상태 | 응답 |
|---|---|---|
| `[쿠키] GET /api/public/naive/me` | 200 | `{"username":"user","isAdmin":false}` |
| `[쿠키] POST /api/public/naive/login` | 200 | `{"username":"user"}` |

- F12 → Network → `login` → Response Headers에 `Set-Cookie: naive_user=user; Path=/`
- F12 → Application → Cookies에 `naive_user` = `user` 줄이 생김
- 비밀번호 칸을 `9999`로 바꾸고 로그인하면 `401 {"error":"아이디 또는 비밀번호가 틀립니다"}` (비밀번호 확인은 제대로 함)

#### 할 일 ②: 쿠키 값을 바꿈
비밀번호 칸을 `1234`로 되돌림. 아래 둘 중 하나로 `naive_user`를 `admin`으로 바꿈
- F12 → Application → Cookies → `naive_user` 줄의 **Value**를 더블클릭 → `admin` → `Enter`
- 또는 F12 → Console에 입력
  ```js
  document.cookie = 'naive_user=admin; path=/'
  ```
② **내 정보**를 다시 누름

#### 확인 ②: 비밀번호 없이 관리자
| 요청 | 상태 | 응답 |
|---|---|---|
| `[쿠키] GET /api/public/naive/me` | 200 | `{"username":"admin","isAdmin":true}` |

- `naive_user=nobody`처럼 **없는 사람**으로 바꿔도 `{"username":"nobody","isAdmin":false}` — 서버는 그런 사람이 있는지도 안 봄
- [ ] 로그인 200, 쿠키에 `naive_user=user`
- [ ] 쿠키를 `admin`으로 바꾸자 `isAdmin:true`

> 비밀번호 확인은 **로그인할 때 한 번**뿐이었고, 그 뒤로는 브라우저가 내는 값을 그대로 믿었음. 브라우저에 둔 값은 **사용자 손 안에 있음.** 고칠 수 있는 값을 믿으려면 ① 서버에 두거나(세션) ② 고치면 티가 나게 **서명**해야 함(토큰, 4-3부터)
>
> 다행히 이 쿠키는 우리가 만든 이 API에서만 믿음. 4일차 세션 체인은 `naive_user`를 모르므로 `/api/admin/stats`에 이 쿠키만 내면 `401`임

### 4-3. JWT 발급하기

> **목적**: 아이디 · 비밀번호를 확인하고 **서명한 토큰**을 돌려줌. 서버는 아무것도 저장하지 않음 (1-2)
>
> **수정**: 빈 파일 `JwtConfig.java` — 서명 키 · 인코더 · **토큰 체인(검사 기능은 아직 없음)** / 빈 파일 `TokenController.java` — 로그인 메서드 하나. 4-4 · 4-5에서 둘 다 늘리므로, 완성본 전체는 4-5에 둠

#### 할 일 전에: 지금 상태
③ 토큰 줄에서 **로그인**
| 요청 | 상태 | 응답 |
|---|---|---|
| `[토큰] POST /api/token/login` | 403 | `{"error":"CSRF 토큰이 없거나 틀립니다."}` |

- 화면은 토큰 로그인에 **CSRF 토큰을 안 실음** (쿠키를 안 쓰는 방식이라서, 1-3). 지금은 `/api/token/**`도 4일차 체인이 맡아서 CSRF 필터에 막힘. 그래서 오늘 토큰 전용 체인이 꼭 필요함

#### 할 일
**① `JwtConfig.java`** — 이 단계의 모습 (역할 주석은 빈 파일에 있는 것 그대로 둠)
```java
package com.kyobo.lab;

import java.nio.charset.StandardCharsets;

import javax.crypto.SecretKey;
import javax.crypto.spec.SecretKeySpec;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.annotation.Order;
import org.springframework.security.config.Customizer;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.oauth2.jwt.JwtEncoder;
import org.springframework.security.oauth2.jwt.NimbusJwtEncoder;
import org.springframework.security.web.SecurityFilterChain;

import com.nimbusds.jose.jwk.source.ImmutableSecret;

/** (빈 파일의 역할 주석 그대로) */
@Configuration // 스프링 설정 클래스. 안의 @Bean 메서드가 만든 객체를 스프링이 보관함
public class JwtConfig {

    private final SecretKey key;

    // 서명 키: application.properties의 jwt.secret 글자를 HS256용 키로 바꿈. 서버만 알아야 함
    public JwtConfig(@Value("${jwt.secret}") String secret) { // @Value: 설정 파일 값을 넣어 줌. 줄이 없으면 Could not resolve placeholder 'jwt.secret'
        this.key = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
    }

    // 토큰 만들기(서명). TokenController가 이 빈을 받아 씀
    @Bean
    public JwtEncoder jwtEncoder() {
        return new NimbusJwtEncoder(new ImmutableSecret<>(key)); // Nimbus = 스프링이 안에서 쓰는 JWT 라이브러리
    }

    // /api/token/** 요청만 맡는 두 번째 보안 필터 체인
    @Bean
    @Order(1) // 4일차 SecurityConfig의 체인보다 먼저 검사함 (숫자가 작을수록 먼저)
    public SecurityFilterChain tokenChain(HttpSecurity http) throws Exception {
        http
                .securityMatcher("/api/token/**")       // 이 체인이 맡을 주소. 빠뜨리면 모든 요청을 가져가서 세션 로그인이 망가짐
                .cors(Customizer.withDefaults())        // 화면(3000)에서 부를 수 있게 WebConfig의 CORS 규칙을 씀
                .csrf(csrf -> csrf.disable())           // 쿠키를 안 쓰는 방식이라 CSRF 대상이 아님 (가이드 1-3)
                .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS)) // 세션을 만들지도 쓰지도 않음
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/api/token/login").permitAll() // 토큰을 받으러 오는 곳은 누구나
                        .anyRequest().authenticated());                  // 나머지 /api/token/**는 로그인(토큰) 필요
        return http.build();
    }
}
```

**② `TokenController.java`** — 이 단계의 모습
```java
package com.kyobo.lab;

import java.time.Instant;
import java.util.List;
import java.util.Map;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.ResponseEntity;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.AuthenticationException;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.oauth2.jose.jws.MacAlgorithm;
import org.springframework.security.oauth2.jwt.JwsHeader;
import org.springframework.security.oauth2.jwt.JwtClaimsSet;
import org.springframework.security.oauth2.jwt.JwtEncoder;
import org.springframework.security.oauth2.jwt.JwtEncoderParameters;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

/** (빈 파일의 역할 주석 그대로) */
@RestController
public class TokenController {

    // 로그인 요청 본문 {"username":"user","password":"1234"}을 담는 그릇
    record LoginRequest(String username, String password) {
    }

    private final AuthenticationConfiguration authConfig;
    private final JwtEncoder encoder;
    private final long ttlSeconds;

    public TokenController(AuthenticationConfiguration authConfig, JwtEncoder encoder,
                           @Value("${jwt.ttl-seconds}") long ttlSeconds) { // 토큰 수명(초). 설정 파일의 jwt.ttl-seconds
        this.authConfig = authConfig;
        this.encoder = encoder;
        this.ttlSeconds = ttlSeconds;
    }

    // 아이디 · 비밀번호 확인 → 서명한 토큰을 돌려줌. 서버는 아무것도 저장하지 않음
    @PostMapping("/api/token/login")
    public ResponseEntity<Map<String, String>> login(@RequestBody LoginRequest req) throws Exception {
        Authentication auth;
        try {
            // 4-2와 같은 방법으로 비밀번호 확인. 성공하면 이름 · 권한(ROLE_USER …)이 든 Authentication이 나옴
            auth = authConfig.getAuthenticationManager().authenticate(
                    new UsernamePasswordAuthenticationToken(req.username(), req.password()));
        } catch (AuthenticationException e) {
            return ResponseEntity.status(401).body(Map.of("error", "아이디 또는 비밀번호가 틀립니다"));
        }
        // 권한 ROLE_USER → "USER" 로 바꿔 토큰에 넣음 (토큰에는 짧은 이름만)
        List<String> roles = auth.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .map(a -> a.replace("ROLE_", ""))
                .toList();
        Instant now = Instant.now();
        // 토큰 내용(클레임). 누구나 읽을 수 있으니 비밀번호는 절대 넣지 않음
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer("security-day5")                 // iss: 누가 발급했나
                .subject(auth.getName())                 // sub: 누구의 토큰인가
                .issuedAt(now)                           // iat: 언제 발급했나
                .expiresAt(now.plusSeconds(ttlSeconds))  // exp: 언제까지 (지금 + 600초)
                .claim("roles", roles)                   // roles: 무슨 역할인가 (우리가 정한 이름)
                .build();
        JwsHeader header = JwsHeader.with(MacAlgorithm.HS256).build(); // 헤더 {"alg":"HS256"}: 키 하나로 서명
        String token = encoder.encode(JwtEncoderParameters.from(header, claims)).getTokenValue(); // 헤더.내용.서명 문자열
        return ResponseEntity.ok(Map.of("token", token));
    }
}
```
- `JwtEncoderParameters.from(header, claims)`에서 `header`를 빼면 인코더가 HS256 키로 서명하지 못해 서버 오류가 남 (화면에는 401 `로그인이 필요합니다`로 보임, 5장). 헤더(HS256)와 키 종류(HmacSHA256)가 맞아야 함

```java
    private JwtAuthenticationConverter rolesConverter() {
        JwtGrantedAuthoritiesConverter authorities = new JwtGrantedAuthoritiesConverter();
        authorities.setAuthoritiesClaimName("roles"); // 기본은 scope · scp 클레임. 우리 토큰은 roles

        converter.setJwtGrantedAuthoritiesConverter(authorities);
        return converter;
    }
```

```java
/**

 *
 * [역할] 토큰(JWT) 방식의 보안 설정
 *   1. 서명 키 (application.properties의 jwt.secret)   → 생성자

 *   4. 토큰의 roles 클레임을 ROLE_ 권한으로 바꾸기        → rolesConverter()
 *
 * [알아야 할 것]
 * - SecurityConfig의 filterChain과 별개로 체인이 하나 더 생김. 요청마다 "처음 맞는 체인 하나"만 씀 (1일차) → @Order(1)로 먼저 검사
 * - 토큰 체인은 쿠키 · 세션을 쓰지 않음 → CSRF 대상이 아니고(끔), 세션도 만들지 않음(STATELESS)
 * - 서명 키를 아는 쪽만 토큰을 만들 수 있음. 키가 새면 누구나 관리자 토큰을 만듦 (운영에서는 환경 변수 · 비밀 저장소에 둠)
 */
@Configuration // 스프링 설정 클래스. 안의 @Bean 메서드가 만든 객체를 스프링이 보관함
public class JwtConfig {

    private final SecretKey key;

    // (4-3) 서명 키: application.properties의 jwt.secret 글자를 HS256용 키로 바꿈. 서버만 알아야 함
    public JwtConfig(@Value("${jwt.secret}") String secret) { // @Value: 설정 파일 값을 넣어 줌. 줄이 없으면 Could not resolve placeholder 'jwt.secret'
        this.key = new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256");
    }

    // (4-3) 토큰 만들기(서명). TokenController가 이 빈을 받아 씀
    @Bean
    public JwtEncoder jwtEncoder() {
        return new NimbusJwtEncoder(new ImmutableSecret<>(key)); // Nimbus = 스프링이 안에서 쓰는 JWT 라이브러리
    }

    // (4-4) 토큰 검사(서명 · 만료). 만들 때와 같은 키로 서명을 다시 계산해 비교함 (HS256 = 키 하나)
    @Bean
    public JwtDecoder jwtDecoder() {
        return NimbusJwtDecoder.withSecretKey(key).build();
    }

    // (4-3) /api/token/** 요청만 맡는 두 번째 보안 필터 체인
    @Bean
    @Order(1) // 4일차 SecurityConfig의 체인보다 먼저 검사함 (숫자가 작을수록 먼저)
    public SecurityFilterChain tokenChain(HttpSecurity http) throws Exception {
        http
                .securityMatcher("/api/token/**")       // 이 체인이 맡을 주소. 빠뜨리면 모든 요청을 가져가서 세션 로그인이 망가짐
                .cors(Customizer.withDefaults())        // 화면(3000)에서 부를 수 있게 WebConfig의 CORS 규칙을 씀
                .csrf(csrf -> csrf.disable())           // 쿠키를 안 쓰는 방식이라 CSRF 대상이 아님 (가이드 1-3)
                .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS)) // 세션을 만들지도 쓰지도 않음
                .authorizeHttpRequests(auth -> auth
                        .requestMatchers("/api/token/login").permitAll()        // 토큰을 받으러 오는 곳은 누구나
                        .requestMatchers("/api/token/admin").hasRole("ADMIN")   // (4-5) 권한 목록에 ROLE_ADMIN이 있어야 함
                        .anyRequest().authenticated())                          // 나머지 /api/token/**는 토큰 필요
                // (4-4) Bearer 토큰을 jwtDecoder로 검사하는 필터를 켬 / (4-5) 토큰 → 권한 바꾸는 방법을 알려 줌
                .oauth2ResourceServer(oauth -> oauth.jwt(jwt -> jwt.jwtAuthenticationConverter(rolesConverter())));
        return http.build();
    }

    // (4-5) 토큰의 roles 클레임 ["ADMIN"] → 권한 ROLE_ADMIN (hasRole("ADMIN")과 맞춤)
    private JwtAuthenticationConverter rolesConverter() {
        JwtGrantedAuthoritiesConverter authorities = new JwtGrantedAuthoritiesConverter();
        authorities.setAuthoritiesClaimName("roles"); // 기본은 scope · scp 클레임. 우리 토큰은 roles
        authorities.setAuthorityPrefix("ROLE_");      // 기본 앞말은 SCOPE_. hasRole은 ROLE_을 찾음
        JwtAuthenticationConverter converter = new JwtAuthenticationConverter();
        converter.setJwtGrantedAuthoritiesConverter(authorities);
        return converter;
    }
}
```

```java
package com.kyobo.lab;

import java.time.Instant;
import java.util.List;
import java.util.Map;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.ResponseEntity;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.core.Authentication;
import org.springframework.security.core.AuthenticationException;
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.annotation.AuthenticationPrincipal;
import org.springframework.security.oauth2.jose.jws.MacAlgorithm;
import org.springframework.security.oauth2.jwt.JwsHeader;
import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.security.oauth2.jwt.JwtClaimsSet;
import org.springframework.security.oauth2.jwt.JwtEncoder;
import org.springframework.security.oauth2.jwt.JwtEncoderParameters;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

/**
 * 5일차 · 05 (같은 로그인, 세 가지 방법)
 *
 * [역할] 토큰(JWT) 방식 API 세 개
 *   - POST /api/token/login : 아이디 · 비밀번호 확인 후 서명한 토큰을 돌려줌 (누구나)
 *   - GET  /api/token/me    : 토큰에서 꺼낸 정보 (토큰 있는 사람)
 *   - GET  /api/token/admin : 관리자 전용 (ADMIN 토큰)
 *
 * [알아야 할 것]
 * - 서버는 로그인 상태를 아무 데도 저장하지 않음. 화면이 토큰을 들고 있다가 요청마다 Authorization: Bearer 헤더에 실음
 * - /me는 DB도 세션도 보지 않음. 서명이 맞는 토큰이면 그 안에 적힌 내용을 그대로 믿음
 * - 토큰 가운데 조각(내용)은 암호화가 아니라 Base64URL 인코딩임 → 누구나 읽음. 비밀번호 · 개인정보를 넣지 않음
 */
@RestController
public class TokenController {

    // 로그인 요청 본문 {"username":"user","password":"1234"}을 담는 그릇
    record LoginRequest(String username, String password) {
    }

    private final AuthenticationConfiguration authConfig;
    private final JwtEncoder encoder;
    private final long ttlSeconds;

    public TokenController(AuthenticationConfiguration authConfig, JwtEncoder encoder,
                           @Value("${jwt.ttl-seconds}") long ttlSeconds) { // 토큰 수명(초). 설정 파일의 jwt.ttl-seconds
        this.authConfig = authConfig;
        this.encoder = encoder;
        this.ttlSeconds = ttlSeconds;
    }

    // (4-3) 아이디 · 비밀번호 확인 → 서명한 토큰을 돌려줌. 서버는 아무것도 저장하지 않음
    @PostMapping("/api/token/login")
    public ResponseEntity<Map<String, String>> login(@RequestBody LoginRequest req) throws Exception {
        Authentication auth;
        try {
            // 4-2와 같은 방법으로 비밀번호 확인. 성공하면 이름 · 권한(ROLE_USER …)이 든 Authentication이 나옴
            auth = authConfig.getAuthenticationManager().authenticate(
                    new UsernamePasswordAuthenticationToken(req.username(), req.password()));
        } catch (AuthenticationException e) {
            return ResponseEntity.status(401).body(Map.of("error", "아이디 또는 비밀번호가 틀립니다"));
        }
        // 권한 ROLE_USER → "USER" 로 바꿔 토큰에 넣음 (토큰에는 짧은 이름만)
        List<String> roles = auth.getAuthorities().stream()
                .map(GrantedAuthority::getAuthority)
                .map(a -> a.replace("ROLE_", ""))
                .toList();
        Instant now = Instant.now();
        // 토큰 내용(클레임). 누구나 읽을 수 있으니 비밀번호는 절대 넣지 않음
        JwtClaimsSet claims = JwtClaimsSet.builder()
                .issuer("security-day5")                 // iss: 누가 발급했나
                .subject(auth.getName())                 // sub: 누구의 토큰인가
                .issuedAt(now)                           // iat: 언제 발급했나
                .expiresAt(now.plusSeconds(ttlSeconds))  // exp: 언제까지 (지금 + 600초)
                .claim("roles", roles)                   // roles: 무슨 역할인가 (우리가 정한 이름)
                .build();
        JwsHeader header = JwsHeader.with(MacAlgorithm.HS256).build(); // 헤더 {"alg":"HS256"}: 키 하나로 서명
        String token = encoder.encode(JwtEncoderParameters.from(header, claims)).getTokenValue(); // 헤더.내용.서명 문자열
        return ResponseEntity.ok(Map.of("token", token));
    }

    // (4-4) 토큰에서 꺼낸 정보를 돌려줌. DB도 세션도 보지 않음
    @GetMapping("/api/token/me")
    public Map<String, Object> me(@AuthenticationPrincipal Jwt jwt) { // @AuthenticationPrincipal: 검사를 통과한 토큰(Jwt)을 넣어 줌
        return Map.of("username", jwt.getSubject(), "roles", jwt.getClaim("roles"), "expiresAt", jwt.getExpiresAt().toString());
    }

    // (4-5) 관리자 전용. 누가 들어올 수 있는지는 JwtConfig의 규칙이 정함
    @GetMapping("/api/token/admin")
    public Map<String, String> admin() {
        return Map.of("secret", "관리자 전용 데이터");
    }
}
```

### 4-6. 재시작 · 만료 · 로그아웃 비교 (코드 없음)

> **목적**: 세션과 토큰을 같은 조건에 놓고 차이를 표로 정리함 (1-1, 1-6)
>
> **수정**: `application.properties`의 `jwt.ttl-seconds`를 **잠깐 `5`로 바꿨다가 `600`으로 되돌림**

#### 할 일 ①: 재시작 비교
1. 아이디 `user`로 ① **로그인**, ③ **로그인** (둘 다 해 둠)
2. 서버 재시작 (화면은 `F5` 하지 않음)
3. ① **내 정보**, ③ **내 정보**

#### 확인 ①
| 요청 | 상태 | 응답 |
|---|---|---|
| `[토큰] GET /api/token/me` | **200** | `{"username":"user","expiresAt":"...","roles":["USER"]}` |
| `[세션] GET /api/me` | **401** | `{"error":"로그인이 필요합니다"}` |

- [ ] 세션은 풀리고 토큰은 그대로

#### 할 일 ②: 로그아웃 비교
1. ① **로그인** → F12 → Application → Cookies에서 `JSESSIONID` 값을 메모장에 복사해 둠
2. ① **로그아웃** → 복사해 둔 번호로 터미널에서 요청
   ```powershell
   curl.exe http://localhost:8080/api/me -H "Cookie: JSESSIONID=복사한값"
   ```
3. ③ **로그인** → 화면의 토큰을 복사해 둠 → ③ **로그아웃(토큰 버리기)** → 복사한 토큰으로 요청
   ```powershell
   curl.exe http://localhost:8080/api/token/me -H "Authorization: Bearer 복사한토큰"
   ```

#### 확인 ②
| 무엇을 | 결과 |
|---|---|
| 로그아웃한 세션 번호로 `/api/me` | `401 {"error":"로그인이 필요합니다"}` ← 서버가 장부에서 지움 |
| 버린 토큰으로 `/api/token/me` | `200 {"username":"user",...}` ← **여전히 유효** |

#### 할 일 ③: 만료
1. `application.properties`에서 `jwt.ttl-seconds=600` → **`5`** 로 바꾸고 서버 재시작
2. ③ **로그인** → 내용(payload)에서 `exp` − `iat` = 5 확인
3. 시계를 보며 **15초 뒤** ③ **내 정보**, **70초 뒤** ③ **내 정보**

#### 확인 ③
| 요청 | 상태 | 응답 |
|---|---|---|
| `[토큰] GET /api/token/me` (70초 뒤) | **401** | (비어 있음) |
| `[토큰] GET /api/token/me` (15초 뒤) | **200** | `{"username":"user","expiresAt":"2026-11-09T01:54:56Z","roles":["USER"]}` |

## 6. 알려진 한계 (면접에서 물어볼 만한 부분)
1. **토큰은 서버가 취소할 수 없음**
   - 로그아웃해도 복사된 토큰은 만료까지 유효함(4-6). 실무에서는 ① 수명을 아주 짧게(5~15분) 하고 **리프레시 토큰**으로 다시 받거나, ② 막을 토큰 목록(블랙리스트)을 서버에 둠 → 10_08에서 다룸
   - 블랙리스트를 두면 서버가 다시 "기억"을 하게 되므로 무상태의 장점이 줄어듦
2. **토큰을 어디에 보관하나**
   - 오늘은 React 상태(메모리)라 `F5`면 사라짐. `localStorage`에 두면 남지만 **XSS 스크립트가 그대로 읽어 감**(4일차). `HttpOnly` 쿠키에 두면 스크립트는 못 읽지만 다시 **쿠키 → CSRF** 문제가 돌아옴. 정답이 하나가 아님
3. **서명 키가 설정 파일에 있음**
   - `jwt.secret`이 저장소에 올라가면 누구나 관리자 토큰을 만듦. 운영은 환경 변수 · 비밀 저장소(Vault 등)에 둠
   - HS256은 **만드는 쪽과 검사하는 쪽이 같은 키**를 가져야 함. 검사하는 서버가 많으면 키도 그만큼 퍼짐 → 공개 키로 검사하는 **RS256**(비대칭)을 많이 씀
4. **토큰의 역할은 발급 시점 기준**
   - 관리자 권한을 뺏어도 이미 발급된 토큰에는 `"roles":["ADMIN"]`이 남아 만료까지 관리자임. 세션은 서버에서 바로 바꿀 수 있음
5. **세션도 여러 서버에서 쓸 수 있음**
   - "세션은 서버가 여러 대면 못 쓴다"가 아니라, 세션을 **공유 저장소(Redis 등, Spring Session)**에 두면 됨. 토큰은 그 저장소가 필요 없다는 것이 차이
6. **순진한 쿠키는 비교용**
   - `NaiveCookieController`는 실제로 쓰면 안 됨. 쿠키에 값을 두려면 서명(예: JWT를 쿠키에) 하거나 서버에 두어야 함
7. **HTTP라서 토큰이 평문으로 오감**
   - `Bearer` 토큰은 "가진 사람이 주인"이라 엿보이면 끝. 운영은 HTTPS 필수 (4일차 HSTS와 같은 이야기)
